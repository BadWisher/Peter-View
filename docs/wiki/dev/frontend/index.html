    Фронтенд на vanilla JS¶

    Эта страница описывает интерфейс сервиса: как он загружается, в каких конвенциях написан и как решаются типовые задачи разработчика. Она нужна тем, кто правит frontend/public/. Здесь приведены порядок загрузки и модель состояния, маршрутизация, конвенции кода, слой доступа к API, работа с долгими задачами, темы и доступность и пошаговая инструкция добавления раздела.

    Страница отвечает на вопросы: где добавить экран, как отправить запрос, почему после правки файл не обновился у пользователя. Развертывание nginx и настройка CSP описаны в Implementation Guide на странице Стек контейнеров, карта модулей для ориентирования находится на странице Карта фронтенда.

    Весь интерфейс занимает каталог frontend/public/: один файл HTML, семнадцать ES-модулей на 4306 строк и один CSS на 4513 строк. Ни Node, ни сборщик, ни фреймворк не используются. Правки подхватываются копированием в контейнер nginx, сборочного шага нет как класса.

    Загрузка страницы и состояние¶

    Файл index.html (58 строк) это фиксированный каркас с тремя контейнерами и sprites-хранилищем. Состав каркаса приведен ниже.

    • #app единственная цель рендера, приложение заменяет его innerHTML.
    • #overlay-root служит для модальных окон.
    • #toast-root служит для всплывающих сообщений.
    • SVG-спрайт из 32 элементов <symbol>; иконки вызываются функцией icon(), который подставляет <use href="#...">.

    Подключение ресурсов сопровождается версионными query-строками, которые поддерживаются вручную: style.css?v=52, js/app.js?v=52, tokens.css?v=48. Любая правка требует поднять номер, иначе браузеры продолжают держать старый кэш. Отдельной константы версии в коде нет.

    Модуль app.js (77 строк) это входная точка. Он выполняет шаги в таком порядке: загружает словарь i18n/{ru,en}.json, обращается к GET /api/auth/me, при успехе догружает /api/styleguides и /api/config (оттуда приходят актуальные признаки разделов), ставит обработчик hashchange и рисует первый экран. При ответе 401 рисуется форма входа.

    Словарь i18n покрывает страницы входа, навигацию, аккаунт и часть административных экранов; остальные строки зашиты в код по-русски.

    Общее состояние всех экранов живет в объекте state (shared.js, строки 57-94). Его содержимое перечислено ниже: пользователь, текущий маршрут, режим источника проверки, флаги групп проверок, текущая задача и отчет, активные гайды, дерево репозитория, спецификации, признаки разделов и тема. Это не стор с подписками: каждый экран читает и пишет состояние напрямую, а перерисовка после изменения полная. Исключения точечные, DOM обновляется напрямую там, где полная перерисовка убивает поток данных (стрим воркеров, бейдж раздела Наблюдение).

    Маршрутизация¶

    Роутинг построен на хеше адреса, History API не используется. Таблица renderers в модуле router.js (44 строки) сопоставляет хеш функции renderX(). Маршруты перечислены ниже: #/check, #/review, #/documents, #/watch/<groupId>[/<pageId>], #/api, #/guides, #/screenshots, #/history, #/insights, #/settings, #/users, #/health.

    Guard'ы расположены в функции currentRoute() модуля shared.js. Правила приведены ниже: маршруты documents, watch, api и screenshots проверяют флаг раздела и уводят на #/check при выключенном разделе; три административных маршрута требуют state.user.role === "admin"; неизвестный путь трактуется как check. Клиентская проверка защищает интерфейс от мусора, а настоящая защита серверная: middleware feature_gate и зависимость require_admin. Обход через адресную строку упирается в ответы 403 и 404.

    Аргументы маршрута разбираются сегментами хеша (у раздела Наблюдение до двух), query-строка внутри хеша отрезается. Функция renderApp() перед каждым рендером снимает модальное окно и атрибут inert с контейнера #app и останавливает сторонние таймеры (опрос мониторинга, слушатель вставки из буфера), кроме таймеров текущего экрана.

    Конвенции записи кода¶

    Ниже приведены правила, которых придерживается код фронтенда.

    • Используются нативные ES-модули с именованными экспортами вида export function renderX и bindX. Классов и default-экспортов нет.
    • HTML собирается шаблонными литералами, вся подстановка пользовательских данных идет через escapeHTML().
    • Двойные кавычки, точки с запятой, стиль именования camelCase. Комментарии пишутся по-русски и объясняют причину решения (почему у iframe атрибут src, а не srcdoc; почему используется data-URL, а не blob-ссылка).
    • После каждого await в асинхронном обработчике проверяется if (state.route !== ...) return, чтобы ответ устаревшего запроса не нарисовался поверх нового экрана.
    • Циклические импорты разрываются объектом hooks (модуль shared.js держит ссылки bindShell и renderApp, которые назначает app.js) и ленивыми вызовами import().
    • На ревью следует помнить об известных шероховатостях: guides.js в ветке ошибки обращается к overlayRoot и app без импорта, а documents.js в режиме предпросмотра вызывает неимпортированный previewApi.

    Слой доступа к API¶

    Единственный вход в сеть это функция api(path, options) (shared.js, строка 675). Его поведение описано пунктами ниже.

    • Запросы идут с credentials:"same-origin".
    • Заголовок JSON ставится только если тело не является FormData; иначе браузер сам подставляет boundary.
    • На неуспешном ответе функция бросает Error с текстом поля detail и свойством .status.
    • Бинарные ответы возвращаются как Blob по значению content-type.
    • CSRF-токен не отправляется нигде: серверная защита это проверка origin, а фронтенд работает с того же источника.

    Ошибки показываются тостом функции showError() в контейнере #toast-root (автозакрытие через 5 секунд, текст экранируется). Занятость кнопок оформляется вызовом setBusy(кнопка, флаг, подпись).

    Отображение долгих задач¶

    Кусок кода в check.js (строки 470-554) требует знания деталей, потому что это единственная часть интерфейса, работающая не по схеме «запрос-ответ». Механика описана пунктами ниже.

    • EventSource("/api/jobs/{id}/stream", {withCredentials:true}) слушает четыре типа событий. Событие start добавляет карточку воркера, delta дописывает текст в карточку, end фиксирует итог воркера и счетчик находок, а finished закрывает поток, забирает GET /api/jobs/{id}/report и переводит экран на #/review.
    • Параллельно тикает опрос GET /api/jobs/{id} раз в 1200 миллисекунд. Если стрим открылся и затем оборвался, показывается тост «Потеряна связь с сервером», и дальнейшая жизнь экрана идет на одном опросе.
    • Дельты не перерисовывают DOM. Имена испачканных воркеров копятся в Set, один вызов requestAnimationFrame на кадр дописывает TextNode в элемент <pre> карточки. Автоскролл выполняется, только когда пользователь находится у нижнего края (48 пикселей до него).

    Кнопка «Отмена» чисто клиентская: она закрывает слушатели, но серверную задачу не убивает.

    Разбор отчета (#/review) принимает данные в любых прежних форматах. Функция normalizedIssues() перебирает алиасы полей (line, line_number, block_index; message, description; fragment, match, span_text; recommendation, replacement, suggestion; engine, source), приводит строгость к трем уровням и сортирует по блоку и позиции. Принять или отклонить замечание означает скрыть или показать его: состояние хранится в state.hiddenIssues, на сервер не пишется ничего. В XLSX уходят видимые строки (запрос POST /api/report-issues).

    Опрос вместо стрима в разделе Наблюдение¶

    Раздел Наблюдение (watch.js, 865 строк) стрима не имеет. Порядок работы экрана описан ниже.

    1. Запуск группы идет запросом POST /api/watch/groups/{id}/run.
    2. Пока group.running истинно, каждые 2000 миллисекунд вызывается setInterval(renderWatch). Роутер снимает интервал при уходе с экрана.
    3. Копия страницы открывается iframe'ом на GET /api/watch/pages/{id}/copy. Серверная HTML-копия отдается со своим CSP (см. конфигурацию nginx).
    4. Переключение «Было» и «Стало» меняет атрибут src на вариант с ?v=old.

    Слияние текстовых хунков и структурных событий в человеческие фразы живет на клиенте (функции watchChanges и watchUiSentence), а сервер отдает сырые данные. Клик по строке изменения подсвечивает узел внутри iframe по атрибуту data-pvwatch-path.

    Темы, i18n и доступность¶

    Дизайн-токены объявлены в tokens.css: 12 зарегистрированных переменных @property, чтобы переключение темы анимировалось. Светлая палитра находится в :root, переопределение темной в html[data-theme="dark"]. Обе темы используют одинаковые семантические имена переменных (--page, --surface, --ink, --primary и другие). Модуль theme-boot.js (10 строк) до первой отрисовки читает localStorage["pv-theme"] и ставит атрибут, иначе экран вспыхнет белым. Файл style.css использует только токены, сырые HEX-цвета внутри компонентов не появляются.

    Доступность реализована по минимуму, но осознанно. Реализованы такие элементы: ссылка-пропуск, aria-live=polite на тостах, role=dialog с aria-modal, захват фокуса и возврат фокуса в модальном окне, перемещение фокуса стрелками (roving tabindex) в меню аккаунта, клавиши j, k и h для навигации по замечаниям в разборе.

    Порядок добавления раздела¶

    Ниже приведен полный проход на примере вымышленного раздела foo. Так же добавлялись разделы documents, api и watch.

    1. В файле backend/app/features.py добавьте "foo" в кортеж OPTIONAL и маппинг переменной FEATURE_FOO. Создайте routers/foo.py с зависимостью Depends(require_feature("foo")) (плюс проверка роли где нужно) и зарегистрируйте роутер в main.py. Если путь нового роутера не начинается со стандартного префикса, дополните список middleware feature_gate.
    2. В файле public/js/shared.js заведите поле state.foo, запись в routeMeta (название и иконка), элемент в navItems или adminItems и строку FEATURE_ROUTES.foo = "foo".
    3. Создайте public/js/foo.js с функцией export async function renderFoo(), которая собирает HTML и вызывает renderShell(...), плюс bindFoo() для обработчиков. Все запросы идут через api().
    4. В public/js/router.js добавьте импорт и строку в таблицу renderers.
    5. В public/index.html добавьте <symbol> новой иконки при необходимости и поднимите параметр ?v= у измененных css и js.
    6. Стили пишите в public/style.css на токенах; в i18n/ru.json и i18n/en.json добавьте ключ nav.foo.
    7. Файл nginx.conf трогать не нужно: catch-all /api/ проксирует новый путь. Отдельный location требуется только для SSE или особых CSP.

    Режим предпросмотра¶

    Параметр ?preview=1 (или путь /preview/) включает демо-режим. В нем появляется выдуманный администратор, все разделы считаются включенными, а функция api() перенаправляется в previewApi(). Это regex-мок на 480 строк внутри shared.js, который выдает фикстуры и двигает статусы задач по номерам опроса. Режим служит живой витриной для GitHub Pages (docs/preview/) и песочницей для верстки без сервера. Ничто не обязывает держать мок синхронным с реальным контрактом, обновляйте его вручную при смене форматов ответов.
