    Бэкенд на FastAPI¶

    Эта страница описывает серверное приложение в каталоге backend/app: как собрано приложение, какие конвенции действуют в слоях кода и как решаются типовые задачи разработчика. Она нужна тем, кто правит серверную часть. Здесь приведены порядок сборки приложения, конвенции роутеров, реализация аутентификации, флаги разделов, слой движков, реестр правил, назначение модулей пакета llm/ и способы запуска диагностических команд.

    Страница отвечает на вопросы: куда добавить новый маршрут, где лежат константы лимитов, как устроено обогащение находок. Как части стыкуются между собой описано в разделе Архитектура, начать стоит со страницы Общая архитектура. Серверное приложение работает одним процессом uvicorn, весь асинхронный код построен на asyncio.

    Сборка приложения¶

    Модуль app/main.py (164 строки) создает объект FastAPI(title="Peter View API", version="0.1.0") и навешивает по порядку три промежуточных слоя. Их назначение приведено ниже.

    1. CORSMiddleware получает источники из переменной PROOFREADER_CORS_ORIGINS; пустое значение означает режим одного источника, allow_credentials включен.
    2. csrf_origin_guard для всех не-GET методов сверяет хост из заголовков Origin или Referer с хостом запроса. Чужой источник получает ответ 403 с текстом «Перекрёстный запрос отклонён». Отдельных CSRF-токенов нет, потому что фронтенд обращается к тому же источнику через nginx.
    3. feature_gate на пути /api/watch*, /api/repo*, /api/api-spec* и /api/screenshot-templates* отвечает 404, когда соответствующий раздел выключен флагом FEATURE_*.

    Дальше идут вызовы include_router для 15 роутеров и два побочника на этапе импорта: auth.seed_default_admin() и styleguide_store.seed_default() создают учетную запись admin/admin при пустой базе и встроенный гайд при пустом хранилище. Обработчики on_event("startup") запускают три фоновых цикла из routers/background.py: автоархивирование репозитория, ежедневное резервное копирование и ежедневный обход мониторинга. Обработчиков остановки нет: при рестарте незавершенные задачи помечаются ошибкой «Прервано рестартом сервера» на следующем старте.

    Документация API (/api/docs, /api/redoc, /api/openapi.json) открыта только при PROOFREADER_DOCS=true. В docker-compose.yml этот флаг зашит в блок environment: со значением false и перекрывает .env.

    Роутеры и их конвенции¶

    HTTP-слой лежит в app/routers/, по файлу на домен. Строки в основных файлах: auth.py 146, checks.py 191, jobs.py 185, repo.py 278, specs.py 257, styleguides.py 192, watch.py 235, остальные меньше. Всего в приложении 89 маршрутов, таблица контрактов находится на странице HTTP API.

    В слое роутеров действуют конвенции, перечисленные ниже.

    • Авторизация оформляется зависимостями FastAPI из auth.py: Depends(require_user) для «нужен вход», Depends(require_admin) для административных ручек, фабрика require_feature("watch") для разделов под флагом.
    • Лимиты входа задаются локально: в infra.py находится константа MAX_UPLOAD_BYTES (50 МиБ), превышение дает ответ 400 с текстом про максимум. Текст и поле prompt тоже режутся на роутере, до начала тяжелой работы.
    • Формы multipart и Form(...) применяются там, где отправляет браузер; JSON-тело там, где клиент программируемый.
    • Долгие задачи роутер не дожидается: POST /api/jobs возвращает {"job_id"} и освобождает соединение, работа продолжается в asyncio.create_task через очередь llm/jobs.py. Стрим прогресса идет отдельным SSE-маршрутом.
    • Ошибки всегда оформляются как HTTPException(status, "человеческое сообщение по-русски"): фронтенд показывает поле detail как есть.
    • Теги OpenAPI проставляет функция custom_openapi() из main.py: префикс пути отображается в тег словарем _PATH_TAGS (модуль openapi_meta.py), плюс добавляется схема CookieAuth на cookie proofreader_session. Публичные маршруты (/api, /api/health, вход, документация) помечены без требования безопасности.

    Чтобы добавить маршрут, создайте функцию в нужном роутере (или новый APIRouter и зарегистрируйте его в main.py), назначьте зависимости и возвращайте словарь. Больше нигде регистрировать маршрут не нужно, потому что автотегирирование и схема безопасности подхватят путь по префиксу.

    Аутентификация и роли¶

    Модуль auth.py занимает 157 строк. Роли в сервисе ровно две, ROLES = ("admin", "editor"). Роль администратора дает доступ к пользователям, настройкам, созданию гайдов и правил; редактору доступно все остальное. Пароли хранятся хешами bcrypt в users.json, константа MIN_PASSWORD равна 8, сложность не проверяется. Учетные записи из OIDC помечаются значением source:"oidc", и смена пароля для них запрещена на уровне роутера.

    Сессии живут в памяти процесса (словарь SESSIONS: dict), cookie называется proofreader_session, токен выдает secrets.token_urlsafe(32), время жизни 12 часов со скользящим продлением на каждом обращении к current_user. Переменная PROOFREADER_COOKIE_SECURE=true добавляет cookie атрибут Secure. Рестарт сервиса завершает все сессии; это осознанное решение, детали приведены на странице Проектные решения.

    Ограничитель перебора находится в routers/session.py: 5 попыток на окно в 300 секунд по ключам ip:username и отдельно ip:*, смена пароля защищена тем же механизмом. Клиентский IP берется из заголовка X-Real-IP, при его отсутствии из первого адреса X-Forwarded-For.

    Модуль oidc.py (110 строк) реализует классический Authorization Code. Этапы работы перечислены ниже.

    1. Конфигурация провайдера получается обращением к OIDC_ISSUER/.well-known/openid-configuration и кэшируется.
    2. Параметры state и nonce хранятся в модульном словаре _pending 600 секунд.
    3. Обмен кода на токены идет методом client_secret_post.
    4. Имя пользователя извлекается из полей preferred_username, email или sub в этом порядке.
    5. Роль admin выдается, если группы пользователя пересекаются со списком OIDC_ADMIN_GROUPS.

    Обратный вызов провайдера мигрирует локальную учетную запись на OIDC по полю oidc_sub и очищает сохраненный пароль.

    Флаги разделов¶

    Модуль features.py (35 строк) содержит кортеж OPTIONAL = ("documents", "api", "watch", "screenshots"), где каждый флаг читается из переменной FEATURE_*. Истиной считаются значения 1, true, yes, on и да. Разделы Вычитка, Гайды, История и Аналитика включены всегда и флагов не имеют. Состояние наружу отдает GET /api/config через features.snapshot(): фронтенд по нему скрывает пункты навигации, а middleware и зависимости держат серверную часть ограничения. Фоновые циклы (автоархив репозитория и ежедневный обход мониторинга) при выключенном флаге не запускаются.

    Слой детерминированных проверок¶

    Модуль checker.py (166 строк) предоставляет фасад check_text(text, user_rules, include_spelling=True). Его поведение описано пунктами ниже.

    • Vale, LanguageTool и пользовательские Python-проверки стартуют параллельно через asyncio.gather(return_exceptions=True). Vale и LanguageTool выполняются задачами цикла событий, Python-движок уходит в поток через default executor. Упавший движок не роняет проверку: его результат просто пустой.
    • Каждая находка обогащается полями реестра (registry_id, guide_section, rule_name, automation, rule_group) и источником. Vale и Python-движок получают источник style-guide, LanguageTool источник spelling с registry_id="LanguageTool.ru", пользовательские регулярные выражения источник custom.
    • Дедупликация работает в два хода. Сначала отбрасывается орфографическое замечание с теми же (line, column, fragment.lower()), что у стилистического: орфографический движок не должен плодить дубли к термину. Затем выполняется точная дедупликация по (line, column, text, rule) между всеми движками.
    • Пользовательские регулярные выражения исполняются пакетом regex (не стандартным re) с тайм-аутом USER_REGEX_TIMEOUT_MS (по умолчанию 200 мс на finditer) и длиной паттерна до 500 символов. Зависший паттерн пропускается, а не подвешивает проверку.

    Движки под фасадом описаны в таблице ниже.

    Модуль Строк Принцип работы
    vale_runner.py 161 Запуск vale --output JSON подпроцессом с конфигом backend/vale/.vale.ini; включены 45 идентификаторов из реестра (engine=vale, выполнение не ручное). Постфильтры убирают: единицы вида Мбит/с у правила Slash_Words, слово «отклик» у UITerms_Click, исключения её, ею, всё, все у LetterYo, латинские аббревиатуры в кавычках. Находка Dash_EmDash переписывается на уровень предложения с заменой на среднее тире
    lt_client.py 221 По одному запросу к LanguageTool на строку, семафор asyncio.Semaphore(8), httpx с тайм-аутом 30 секунд. Если хост недоступен целиком, в лог идет предупреждение, а список находок пустой. Отображение категории в строгость: опечатки и орфография error, грамматика и пунктуация warning, стиль и типографика suggestion
    custom_checks.py 394 pymorphy3 и razdel; пять вызываемых функций: check_anthropomorphism, check_sentence_length (свыше 25 слов), check_formal_you, check_adj_noun_agreement, check_subject_verb_agreement. Функция check_passive_voice в файле есть, но не вызывается, потому что правило помечено в реестре как ручное

    Модуль извлечения текста extractors.py (278 строк) понимает четыре формата. DOCX читается python-docx с обходом XML: сохраняются таблицы и вложенные списки. HTML разбирает BeautifulSoup с lxml: вырезаются узлы nav, footer, header, aside, скрытые элементы и узлы с class или id, похожими на навигационные. MD и TXT читаются как есть. Файл DOCX проходит защиту от zip-бомбы: до 300 МиБ разархивированного содержимого, степень сжатия до 200 раз, до 2000 записей. Разбор в блоки для конвейера модели это отдельная логика (llm/documents.py, описана на странице Конвейер проверки моделью), здесь же текст становится плоскими строками для движков.

    Краулер crawler.py (191 строка) обслуживает маршрут /api/check-url. Его параметры перечислены ниже: обход в ширину по домену, MAX_PAGES=200, MAX_CONCURRENT=5, 20 секунд на страницу, robots.txt с User-Agent Proofreader/1.0, пропуск около 40 бинарных расширений, нормализация URL срезанием query и fragment, остановка после 10 пустых батчей подряд. Каждый запрос идет через net_guard.safe_get.

    Модуль net_guard.py (157 строк) реализует защиту от обращений к внутренним сервисам. Правила перечислены ниже: допускаются только http и https, хост резолвится, и каждый адрес проверяется (loopback, link-local вместе с адресами метаданных облаков 169.254 и fe80::, multicast и reserved отсекаются). Приватные сети по умолчанию разрешены (PROOFREADER_SSRF_ALLOW_PRIVATE=true), потому что сервис рассчитан на интранет. Редиректы шагаются вручную (follow_redirects=False) с перепроверкой каждого перехода; POST на кодах 301, 302 и 303 понижается до GET; тело читается потоково с лимитом PROOFREADER_MAX_FETCH_BYTES (10 МиБ).

    Реестр правил¶

    Модуль style_guide_registry.py занимает 817 строк и содержит 56 встроенных правил списка RULES плюс запись слоя орфографии LanguageTool.ru, итого 57 записей. Поля записи: id, section, group, name, rule, engine (vale, python или manual), automation (automatic, partial или manual), severity, generalization, примеры хороших и плохих текстов. Служебные поля: categories, tasks, scope, priority (error соответствует 90, warning 60, suggestion 40), machine_verifiable, relationships, conflict_family. У некоторых правил есть constraints: например, запрещенный символ длинного тире, требуемое среднее тире и запрещенное к внесению буквенное сочетание.

    Вспомогательные функции модуля: get_rule, enabled_vale_rule_ids (45 идентификаторов), style_guide_rule_ids (52), get_registry(include_spelling). Согласованность реестра с файлом styleguide/rules.yaml поддерживает тест, подробности на странице Правила Style Guide в коде.

    Модули пакета llm¶

    Пакет llm/ самая большая часть бэкенда (25 модулей). Его устройство изложена страницами Конвейер проверки моделью, Детерминированные движки проверки, Клиент модели и кэширование и Прикладные подсистемы. Здесь приведена ответственность каждого модуля, чтобы искать код по задаче.

    • documents.py (717 строк) превращает вход в объект Document со списком Block {index, raw, plain, metadata}. Определяются типы блоков, форматирование и лимиты: 16 000 символов структурированной выдержки и 2000 на блок.
    • chunking.py (167 строк) делит блоки на фрагменты: 8 блоков во фрагменте, перекрытие 2, атомарными считаются «введение плюс список». Функция compress() строит каркас из первых 12 слов блока.
    • pipeline.py (471 строка) планировщик версий: читает PIPELINE_VERSION (значение по умолчанию v2) и PIPELINE_SHADOW. Здесь же проживает версия v1 (8 воркеров и критик) ради откатов и теневого сравнения по ключу (block_index, rule_id, replacement).
    • pipeline_v2.py (698 строк) стадии версии v2 из PIPELINE_V2_STAGES в порядке: evidence, retrieval, finders (language, structure, guide_local по фрагментам; terminology и consistency по документу), verifier батчами по 12 (VERIFY_BATCH), разрешение конфликтов (relationships.supersedes/specializes, conflict_family, rule_precedence_key), сборка отчета. Каждый проход повторяется: PASS_TIMEOUT=360, PASS_RETRIES=2, задержка min(10, 2^n).
    • workers.py (457 строк) вызывает модель по шаблонам Jinja2: каталоги prompts/v1/ (system_base, worker_1..worker_8, extractor) и prompts/v2/ (system_base, language, guide_local, structure, consistency, terminology, verifier). Переменная PROMPT_VERSION переключает шаблонный каталог.
    • client.py (461 строка) совместимый с OpenAI клиент: семафор llm_concurrency, MAX_RETRIES=5, задержка при ограничении частоты min(30, 3*2^n), при исчерпании токенов min(45, 5*2^n). Кэш ответов двух уровней: память на 1024 записи и SQLite stats.db:llm_cache; ключ это sha256 от модели, пространства имен, system и user промптов, а пространство имен склеено из версий конвейера, промптов и подбора правил, поэтому смена RAG_CONFIG_VERSION инвалидирует кэш. Отказ сервера от json_mode или параметра рассуждения запоминается в _unsupported. Стриминг отдает дельты до первой фигурной скобки.
    • evidence.py (105 строк) мост детерминированных движков в схему кандидатов модели: collect_engine_evidence прогоняет checker по блокам с фильтром по guide.effective_ids, а collect_lexicon_evidence ищет запрещенные термины по границе слова.
    • jobs.py (278 строк) очередь и стрим: SQLite jobs.db с таблицей jobs (id, source, status, stage, report, error, created_at), TTL один час, JOB_TIMEOUT_SECONDS=900, потолок блока стрима 20 000 символов с подрезкой начала. События SSE называются start, delta, end, finished.
    • schemas.py (191 строка) нормализует кандидата и отбрасывает выдумки: span_text вне текста блока, неизвестный rule_id, правка, равная оригиналу, нарушение constraints правила. Строгость модели (blocker, suggestion, minor) отображается в уровень интерфейса (error, warning, suggestion).
    • rag.py (451 строка) гибридный поиск правил по гайду: три эмбеддинга на правило (identity, policy, examples), счет 0.55*lexical + 0.45*semantic, надбавки по метаданным, три яруса отката: hybrid, lexical_only, all_rules. Индекс живет в памяти и пересобирается по хешу содержимого.
    • settings.py (153 строки) 11 настраиваемых полей (модель, эмбеддинги, тайминги). Файл llm_settings.json лежит поверх значений окружения, секреты маскируются флагами *_set, слушатели (client, rag) сбрасывают кэш при изменении.
    • stats.py (403 строки) база stats.db: таблица token_usage с атрибуцией через contextvars по пользователю, задаче и воркеру; далее rule_hits, check_history (50 записей на пользователя), doc_views, llm_cache.
    • repo_store.py (532 строки) файловая библиотека документов repo/ (folders.json, docs с JSON-метаданными, blob-файлы, zip-архив). Лимит файла 25 МиБ, автоархивирование через 90 дней.
    • Модули api_specs.py, openapi_fields.py и api_review.py (807 строк суммарно) обслуживают раздел Спецификации API: парные YAML на русском и английском через ruamel в round-trip режиме (ключ поля это path_str), сверка единообразия по именам и текстам, сравнение с учетом разбора, батчи перевода и обзора по 20 сегмента, точечная перезапись YAML с сохранением переводов строк и блочных скаляров.
    • watch_store.py (585 строк) база watch.db (таблицы groups, pages, snapshots, meta, fonts): пароли порталов скрыты XOR с ключом HMAC от PROOFREADER_SECRET, 14 снимков на страницу. watch_run.py (563 строки) httpx плюс перерендер Chromium всегда, определение дублей по хешам содержимого и структуры. watch_dom.py (669 строк) структурное сравнение и деперсонализация (телефоны, почты, номера карт, СНИЛС, ИНН), генерация HTML-копии. watch_render.py (154 строки) ленивый общий экземпляр Chromium и навигационный guard поверх net_guard.
    • extractor.py (260 строк) и extract_jobs.py (270 строк) извлекают гайд из DOCX: куски по 3500 символов, промпт-экстрактор, слияние по парам (заголовок, правило), таблица задач в extract_jobs.db.
    • styleguide_store.py (447 строк) хранит гайды администратора и пользователя в data/styleguides/, вычисляет effective_ids и разрешает конфликты поверх встроенного реестра.
    • shot_templates.py (105 строк) пресеты ширины скриншотов в файле screenshot_templates.json.

    Хранилище данных¶

    Все состояние лежит в томе backend-data, примонтированном в /app/data. Состав: users.json, rules.json, user_prefs.json, llm_settings.json, audit.jsonl, screenshot_templates.json, базы jobs.db, stats.db, watch.db, extract_jobs.db, каталоги styleguides/, repo/, uploads/ и файл-ключ watch.db.key (или секрет PROOFREADER_SECRET из окружения). Схема, размеры и владение описаны на странице Хранилище данных.

    Регрессионные проверки и аудит сайта как CLI¶

    Две диагностические команды запускаются внутри контейнера backend. Блок ниже показывает их.

    docker compose exec backend python -m app.regression_checks   # 44 кейса, код возврата 1 при провале
docker compose exec backend python -m app.site_audit https://example.com --max-pages 40

    Первая команда входит в состав CI (make regression), вторая это разовый обход живого сайта с JSON-сводкой по правилам.
