    Развертывание¶

    Эта страница описывает установку и первый запуск сервиса на сервере. Она нужна администратору, который поднимает Peter View для команды. Здесь приведены требования к хосту, порядок первого запуска, особенности работы за корпоративным прокси, варианты использования готовых образов, структура стека после запуска и набор команд Makefile.

    Страница отвечает на вопросы: что должно быть на сервере, как запустить сервис, что делать, если хост без прямого доступа в интернет, и как управлять уже поднятым стеком. Детали compose-файлов и образов вынесены на страницу Стек контейнеров, полный справочник переменных на страницу Переменные окружения. Поддерживается единственный сценарий развертывания: docker compose на одном хосте. Схемы kubernetes, systemd и установка на «голую» машину документацией не покрыты и не тестировались.

    Требования¶

    Параметры хоста, необходимые для запуска, показаны в таблице ниже.

    Параметр Значение
    Docker Engine с дополнением compose версии 2; скрипт понимает и прежнюю команду docker-compose
    Память 1.5 гигабайта на LanguageTool (JVM получает параметры Xms 512m и Xmx 1g) плюс до 2 гигабайт на приложение backend; фронтенд легкий
    Диск около 2 гигабайт на образы (в образ backend входят Chromium и Playwright), плюс том данных и каталог ./backups
    Порт 3080 по умолчанию (переменная PROOFREADER_PORT); наружу публикуется только порт nginx
    Сеть доступ к реестру загрузок образов; для хоста за корпоративным прокси см. раздел ниже

    Первый запуск¶

    Клонирование и запуск выполняются командами из блока ниже.

    git clone https://github.com/BadWisher/Peter-View
cd Peter-View
./deploy.sh

    Скрипт deploy.sh идемпотентен: он служит и для первичного запуска, и для обновления. Его шаги перечислены ниже.

    1. Скрипт читает значение PROOFREADER_PORT из файла .env (последняя строка побеждает, кавычки вырезаются). Значение по умолчанию 3080.
    2. Определяется доступная compose-команда: сначала docker compose, затем docker-compose, при отсутствии обеих работа завершается ошибкой.
    3. Если файла .env нет, скрипт копирует .env.example и напоминает заполнить LLM_BASE_URL, LLM_API_KEY и переменные эмбеддингов, включить PROOFREADER_COOKIE_SECURE за TLS и PROOFREADER_CORP_PROXY на хосте с прокси.
    4. Если в .env установлено PROOFREADER_CORP_PROXY=true, к командам добавляется overlay docker-compose.corp-proxy.yml.
    5. Стек поднимается с пересборкой образов (команда up -d --build); compose пересобирает только измененные слои.
    6. Скрипт ждет до 60 секунд ответа адреса http://localhost:PORT/ (при наличии в системе curl) и печатает все доступные адреса: localhost, непубличные IPv4 и hostname, без docker-мостов.

    После запуска сервис доступен по адресу http://localhost:3080. Первый вход выполняется под учетной записью admin с паролем admin, о чем напоминает и сообщение скрипта. Смените пароль до подключения пользователей: порядок работы с учетными записями описан в User Guide на странице Учетные записи и роли.

    Примечание к ожиданию готовности. Фронтенд стартует после backend, backend после здоровой службы LanguageTool с start_period 90 секунд. На первой сборке холодный старт не укладывается в 60 секунд ожидания, и скрипт напечатает сообщение «не ответил за 60 с» при полностью здоровом процессе. Это не ошибка, код возврата все равно ноль, состояние смотрите командой make logs.

    Работа за корпоративным прокси¶

    Хосты с доступом в интернет только через прокси (например 127.0.0.1:3128) требуют прокси в двух местах: во время сборки (apt, pip, загрузка Chromium) и во время работы (запросы к модели и эмбеддингам). Overlay docker-compose.corp-proxy.yml закрывает обе потребности. Его состав описан ниже.

    • Поднимается сервис proxy-bridge (alpine/socat) на адресе 172.17.0.1:3128, который форвардит трафик в CORP_PROXY_UPSTREAM (по умолчанию 127.0.0.1:3128).
    • Сервис backend получает настройку build.network: host и запись extra_hosts с host.docker.internal:host-gateway.
    • Backend получает переменные HTTP_PROXY и HTTPS_PROXY со значением http://host.docker.internal:3128 и переменную NO_PROXY со списком localhost,127.0.0.1,backend,languagetool.

    Включение простое: установите PROOFREADER_CORP_PROXY=true в файле .env и выполните ./deploy.sh (или make deploy). Проверить конфигурацию без запуска можно командой make config-corp-proxy.

    С мостом proxy-bridge обращайтесь осторожно: это открытый без аутентификации прокси на docker-интерфейсе. Любой, кто дотянется до адреса 172.17.0.1:3128, выйдет в интернет через ваш корпоративный прокси. Не поднимайте его на хостах с доступной снаружи bridge-сетью.

    Готовые образы вместо сборки¶

    CI публикует образы на GitHub Container Registry: ghcr.io/<владелец>/backend:<sha> и тег :main, на релизах добавляется тег версии. Развертывание из реестра вместо локальной сборки выполняется командами из блока ниже.

    export IMAGE_SHA=<полный commit sha>
export GHCR_REPOSITORY=<владелец/имя в нижнем регистре>
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d

    Overlay prod подменяет поле image: у сервисов backend и frontend (присутствует pull_policy: always) и требует обе переменные: без них compose останавливается и печатает подсказку из конструкции :?. Проверка связки конфигов: make prod-config.

    Структура стека после запуска¶

    Три контейнера работают в одной изолированной bridge-сети internal. Состав стека показывает таблица ниже.

    Сервис Роль Порт
    frontend nginx: статика интерфейса и обратный прокси /api/ единственный опубликованный: 3080->80
    backend FastAPI с Vale, pymorphy3 и Playwright/Chromium внутри 8000, только внутри сети
    languagetool LanguageTool 6.x (образ закреплен по digest), только русский профиль 8010, только внутри сети

    Том backend-data (именованный volume) примонтирован в /app/data, каталог ./backups монтируется в /app/backups. Подробности образов, compose-файлов и nginx находятся на странице Стек контейнеров.

    Команды Makefile¶

    Все обертки над compose собраны в Makefile; они автоматически добавляют overlay корпоративного прокси при соответствующем флаге в .env. Набор команд показан в таблице ниже.

    Команда Действие
    make deploy тот же ./deploy.sh
    make down, make ps, make logs остановить, показать статус, смотреть лог (logs -f)
    make update git pull --ff-only и запуск ./deploy.sh
    make backup архив всего /app/data в ./backups/manual-<время>.tgz
    make config проверка валидности compose-конфига (--quiet)
    make lint, make test, make regression линтер, pytest на хосте, регрессия правил внутри контейнера
    make ci-local lint, test, обе валидации конфига и полная пересборка образов

    У команды make backup есть особенность, о которой нужно помнить. Файлы manual-*.tgz не попадают под автоматическую ротацию (ротация знает только про peterview-*.tar.gz) и копятся до ручного удаления. Подробности на странице Резервное копирование и восстановление.

    Отсутствующие механизмы развертывания¶

    Перечисленные ниже свойства в скрипт сознательно не включены, и оператор учитывает их при планировании.

    • HTTPS: nginx слушает порт 80, сертификатов нет, терминация TLS лежит на внешнем прокси (см. страницу TLS и обратный прокси).
    • Инсталляционных хуков: нет предварительной проверки версии Docker, свободы порта и объема диска.
    • Отдельного шага миграций: схему данных (JSON и SQLite) мигрирует код приложения, отдельного шага обновления нет.
