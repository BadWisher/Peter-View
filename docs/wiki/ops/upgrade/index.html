    Обновление версии¶

    Эта страница описывает цикл обновления развернутого сервиса. Она нужна администратору, который переносит Peter View на новую версию кода или образов.

    Обновление бывает двух видов: пересборка из исходников в git или перетягивание готовых образов из реестра GHCR. Оба пути оставляют том backend-data на месте, поэтому данные не теряются. Отдельных скриптов миграции схемы базы нет: код приложения сам читает старые форматы JSON и SQLite.

    Подготовка¶

    Четыре действия перед обновлением.

    1. Снимите резервную копию командой make backup. Ручные снимки с префиксом manual- автоматика не удаляет, поэтому почистите каталог ./backups после удачного обновления.
    2. Убедитесь, что автоматический снимок свежий. Проверьте раздел Система (строка о резервной копии) или выполните ls ./backups.
    3. Залогиньтесь заранее. Обновление перезапускает backend, и все сессии сбрасываются, потому что живут в памяти процесса.
    4. Предупредите пользователей о начале работ. Идущие в момент перезапуска проверки прервутся: задачи получат статус «Прервано рестартом сервера, запустите проверку заново» и не продолжатся сами, их нужно перезапустить.

    Обновление из исходников¶

    Этот путь подходит для dev-окружений и для площадок, где сервер собирает образы сам.

    make update

    Команда выполняет git pull --ff-only с последующим ./deploy.sh. Скрипт пересобирает измененные слои образов и перезапускает контейнеры. Если pull не fast-forward (есть локальные правки или история разошлась с upstream), git откажет, и это ожидаемое поведение. Разрешите расхождение руками, а не командой reset --hard, иначе потеряете локальные изменения.

    Обновление из образов¶

    Этот путь предназначен для продакшена, где сборки на хосте нет.

    export GHCR_REPOSITORY=<владелец/имя>
export IMAGE_SHA=<новый commit sha>
make prod-config   # проверка связки compose-файлов
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d

    Compose пересоздает контейнеры backend и frontend из новых образов. Сервис languagetool не меняется: его образ закреплен по digest в базовом файле. Политика pull_policy: always гарантирует, что указанный тег действительно перетягивается, а не берется из локального кэша.

    Проверка после обновления¶

    После перезапуска выполните четыре проверки в порядке от дешевых к дорогим.

    docker compose ps                    # все три контейнера healthy
curl -s localhost:3080/api/health    # {"status":"ok","version":"0.1.0"}
make regression                      # самотесты правил внутри backend

    Затем прогоните одну короткую контрольную проверку на вкладке Текст и дождитесь завершения LLM-воркеров, если модель подключена. Этот набор ловит типичные регрессии обновления: LanguageTool не поднялся, ключ модели пропал, формат ответа модели не разбирается.

    Откат¶

    Откатывается каждая половина отдельно.

    • Данные возвращаются снимком резервной копии в порядке со страницы Резервное копирование и восстановление.
    • Образы переключаются значением IMAGE_SHA на предыдущий коммит. Перед обновлением сохраните вывод git log --oneline, чтобы знать предыдущий sha.

    Учтите зависимость фронта от бэкенда. Откат фронтенда без отката бэкенда иногда ломает контракты: новые клиенты совместимы со старыми ответами сервера, а обратное не гарантировано. Безопаснее откатывать обе половины вместе.

    Типичные неполадки после обновления¶

    Симптомы и вероятные причины собраны в таблице.

    Симптом Вероятная причина
    deploy.sh пишет, что фронт не ответил за 60 с, при живых контейнерах LanguageTool долго стартует на холодном кэше; подождите и посмотрите make logs
    Проверки падают на воркерах модели настройки модели живут в томе и переживают обновление, но если том backend-data создавали с нуля, ключ и модель пропали
    /api/docs не открывается значение PROOFREADER_DOCS=false зашито в compose-файл, см. страницу Переменные окружения
    Ответ 403 «Перекрёстный запрос отклонён» после смены адреса вы поменяли хост или порт, а браузер шлет старый origin; обновите закладки и проверьте проброс Host на внешнем прокси

    Связанные разделы¶

    Страницы, продолжающие тему обновлений.

    • Развертывание описывает deploy.sh и цели Makefile целиком.
    • Резервное копирование и восстановление нужно перед обновлением и служит путем отката данных.
    • Стек контейнеров объясняет закрепление образов по digest и production-overlay.
    • Дежурство и разбор инцидентов описывает действия, если обновление пошло не так.
    • Жесткая настройка для публичного хоста требует регулярно пересобирать закрепленные образы.
