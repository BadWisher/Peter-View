    Прикладные подсистемы¶

    Эта страница описывает четыре подсистемы, которые живут по краям ядра проверки: репозиторий документов, связки OpenAPI, мониторинг страниц и шаблоны скриншотов. Она нужна тем, кто читает код этих модулей или разбирается в потоке данных раздела. Здесь по каждой подсистеме приведены назначение, хранение, поток данных и точки входа API.

    Страница отвечает на вопросы: где физически лежат документы и снимки, как устроены сравнение версий и обход по расписанию. Поведение этих разделов в интерфейсе описано в User Guide на странице Дополнительные разделы интерфейса и на страницах соответствующих разделов. Каждый модуль включает свои эндпоинты только под флагом окружения.

    Репозиторий документов¶

    Модуль llm/repo_store.py работает под флагом FEATURE_DOCUMENTS. Он хранит проверяемые файлы с иерархией папок и версиями. Все данные лежат на файловой системе в data/repo/, метаданные записаны в JSON-файлах того же дерева, отдельная база данных не заводится.

    Устройство подсистемы описано пунктами ниже.

    • Каталог data/repo/ отражает структуру: папки это директории, чей идентификатор равен пути и защищен регулярным выражением от ../. Документы хранятся поддоном с идентификатором, а версии получают имена вида <doc>/<n>.<ext> вместе с метаданными.
    • Метаданные версии включают название, примечание, ссылку на задачу Jira, автора, время создания, номер версии, признак kind (upload или review) и пометку seen для каждого пользователя, из которой растет отметка «новое».
    • Лимит размера файла задает REPO_MAX_FILE_BYTES (25 МиБ). Суммарный объем хранилища не лимитирован, за диском следит администратор через раздел Система.
    • Фоновый цикл из routers/background.py раз в 6 часов переносит в архив документы, к которым не обращались дольше REPO_ARCHIVE_AFTER_DAYS (90 дней).
    • Поиск GET /api/repo/search?q= работает простой подстрокой по именам, без индекса.
    • Скачивание версии идет прямым GET с двойным заголовком Content-Disposition (ASCII и UTF-8 filename*), что дает корректные русские имена файлов.

    Связки спецификаций OpenAPI¶

    Модули llm/api_specs.py, api_review.py и openapi_fields.py работают под флагом FEATURE_API. Связка скрепляет два документа из репозитория: русскую и английскую версии одной OpenAPI-спецификации.

    Механика описана пунктами ниже.

    • Модуль api_specs.py разбирает YAML безопасным загрузчиком и выделяет сегменты. Сегмент это именованный фрагмент: описание пути, операции или схемы с парой русского и английского текста. Ключом сегмента служит путь с методом и полем (или имя схемы и поля). Проверяемые поля: description, summary, имена параметров и подобные.
    • Модуль openapi_fields.py сравнивает связку: обходит дерево RU и EN и находит расхождения. Типовые расхождения перечислены здесь: поле есть в одной версии и отсутствует в другой, описание различается при пустом переводе, рядом встречаются термины-синонимы.
    • Версионирование: связка помнит предыдущую пару версий (признак has_previous), а метод diff отдает измененные пути с русским и английским текстом.
    • Режимы разбора моделью (api_review.py). Команды ai-review и translate используют не собственных воркеров, а generic-задачу через llm_jobs.submit_task (тот же механизм очередей jobs с опросом /api/jobs/{id}). Модель получает измененные сегменты из диффа и возвращает замечания или переводы. Отдельного конвейера у подсистемы нет.
    • Выгрузка правок: POST .../download с полем edits вида (сегмент: новый текст) применяет точечные замены к последней версии YAML и отдает файл <base>_edited.yaml. Это текстовые правки, а не переформатирование спецификации.

    Мониторинг страниц¶

    Модули llm/watch_store.py, watch_run.py, watch_dom.py и watch_render.py работают под флагом FEATURE_WATCH. Подсистема скачивает живые страницы, сравнивает снимки и хранит историю изменений.

    Хранение. База SQLite data/watch.db содержит три сущности: группы (название, способ входа none, form или basic, адрес страницы входа, логин, пароль, имена полей формы), страницы (идентификатор группы, URL, заголовок, признак активности) и снимки (идентификатор страницы, метка времени, текст, DOM, находки в JSON, признак текущего). На страницу сохраняется WATCH_SNAPSHOT_KEEP снимков, по умолчанию 14. Пароли и снимки маскируются потоком XOR по ключу HMAC от PROOFREADER_SECRET; границы применимости такой защиты описаны на странице Механизмы защиты.

    Обход. Для одной страницы запрос идет через safe_request из модуля net_guard, то есть через ту же SSRF-защиту, что и проверка по URL в ядре. Вход через форму выполняется safe_post на страницу входа с полем и паролем, полученные cookie подхватываются сессией; при basic-входе добавляется заголовок Authorization. Текст извлекает watch_dom.py на lxml: берется видимый текст и структура элементов с атрибутами CSS-путей. Действуют лимиты WATCH_TEXT_CAP и WATCH_DOM_CAP.

    Сравнение. Текущий снимок сопоставляется с предыдущим по двум осям. Текстовая ось делит снимки на строки и считает diff-хунки. Структурная ось выдает UI-события: изменение текста, добавление, удаление, сдвиг, смену тега или атрибута, привязанные по атрибуту data-pvwatch-path. События, покрытые текстовыми хунками, дедуплицируются. Фразы на русском («Добавлено: ...») из сырых данных собирает фронтенд; логика watchUiSentence описана на странице Карта фронтенда, а сервер отдает только данные.

    Копия и снимок. Модуль watch_render.py отрисовывает сохраненную страницу для iframe по пути .../copy с подсветкой по data-pvwatch-path. PNG-снимок по пути .../shot делает Playwright с headless Chromium: тайм-аут задает PROOFREADER_WATCH_RENDER_TIMEOUT (25 секунд), стабильность страницы ожидает ..._SETTLE_MS (1200 миллисекунд). Chromium устанавливается в Dockerfile; без него подсистема отвечает кодом 503.

    Расписание. Фоновый обход всех групп запускается в час PROOFREADER_WATCH_HOUR (по умолчанию 4 часа утра) циклом background.start_watch_daily. Ручной запуск идет POST .../run. Действует единственный внутрипроцессный замок _watch_running: параллельно обход не выполняется, а вторая команда вернет статус running.

    Шаблоны скриншотов¶

    Модуль llm/shot_templates.py работает под флагом FEATURE_SCREENSHOTS и намеренно тонкий. Сервер хранит только шаблоны ширины в файле data/screenshot_templates.json с полями name и width; значения по умолчанию 800 и 1200 пикселей, валидация допускает от 50 до 4000 пикселей. Обработка изображений (обрезка, замазывание, пипетка) полностью клиентская, на canvas фронтенда. Ни один пиксель картинки на сервер не отправляется.

    Связанные разделы¶

    Страницы, продолжающие тему подсистем.

    • Механизмы защиты SSRF-защита net_guard и маскирование данных мониторинга.
    • Хранилище данных где физически лежат файлы и таблицы подсистем.
    • Карта фронтенда экраны разделов и клиентская логика.
    • HTTP API контракты эндпоинтов подсистем.
