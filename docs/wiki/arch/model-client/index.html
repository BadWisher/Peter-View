    Клиент модели и кэширование¶

    Эта страница описывает модуль backend/app/llm/client.py, единственную точку выхода сервиса в языковую модель, и модуль backend/app/llm/rag.py, клиент эмбеддингов для подбора правил. Страница нужна тем, кто читает код обращения к модели, настраивает параллельность и тайм-ауты или разбирается в расходе токенов.

    Страница отвечает на вопросы: как формируется запрос к модели, что происходит при отказе провайдера, как устроен кэш и почему одинаковый промпт не уходит в модель повторно. Пользовательская часть настроек описана в разделе User Guide на странице Языковая модель, переменные окружения в Implementation Guide на странице Переменные окружения.

    Оба модуля работают через совместимые с OpenAI HTTP-API. Адреса и ключи задает администратор.

    Обращения к модели¶

    Транспорт реализован пакетом openai: клиент AsyncOpenAI создается со значениями base_url = llm_base_url и api_key = llm_api_key. Подходит любой провайдер, у которого есть совместимый с OpenAI метод /chat/completions.

    Основной вызов¶

    Метод complete_json(system, user, on_delta=None) используется всеми воркерами конвейера. Его поведение описано пунктами ниже.

    • Ответ разбирается как JSON. Функция _extract_json вытаскивает объект из произвольного текста ответа и допускает markdown-обертки.
    • При включенном llm_json_mode к запросу добавляется response_format={"type":"json_object"}.
    • Если провайдер отклоняет режим JSON или параметр рассуждения, включается деградация попыток: сначала запрос идет как есть, затем без json_mode, затем без параметра рассуждения.
    • При непустом llm_reasoning_effort (low, medium или high) параметр передается. Модели без рассуждений игнорируют его, а провайдер может отклонить запрос; тогда вызов повторяется без параметра.

    Стриминг¶

    Если вызывающий передал колбэк on_delta, запрос выполняется с stream=True, и в колбэк передаются токены живого текста рассуждений воркера, а не финальный JSON. Так в карточке воркера у пользователя печатается текст в реальном времени. Если провайдер не поддерживает стриминг и отвечает BadRequestError, клиент деградирует до обычного вызова create.

    Параллельность и ретраи¶

    Параллельность ограничивает семафор _semaphore = Semaphore(llm_concurrency). Он пересоздается при изменении настроек через подписку на них.

    Число попыток задает MAX_RETRIES. Формулы пауз между попытками различаются по классу ошибки и приведены ниже.

    • RateLimitError и APITimeoutError: пауза min(30, 3 * 2^n) секунд.
    • Ошибки, похожие на исчерпание лимита токенов, в том числе HTTP 402: пауза min(45, 5 * 2^n) секунд.
    • Временные APIError: пауза min(30, 3 * 2^n) секунд.
    • Разобранный с ошибкой JSON: пауза 1 секунда и повтор.

    Прочие ошибки считаются фатальными: клиент бросает LLMRequestError с обезличенным сообщением, чтобы текст провайдера не попадал в интерфейс.

    Двухуровневый кэш¶

    Кэш устроен по хешу тройки (system, user, temperature) и имеет два уровня. Их свойства перечислены ниже.

    • Первый уровень это словарь _cache в памяти процесса, вытеснение FIFO, вместимость CACHE_MAX, равная 1024 записям.
    • Второй уровень персистентный: он пишется в базу функцией stats.cache_set и переживает перезапуск.

    Одинаковый промпт не уходит в модель повторно. Это экономит токены и одновременно служит источником согласованности: если изменилась только версия промпта, хеш становится другим и запись кэшируется заново, то есть устаревшие ответы не подмешиваются.

    Учет токенов¶

    На каждый ответ вызывается stats.record_tokens(prompt, completion, cached). У части провайдеров значение cached_tokens лежит в поле prompt_tokens_details. Агрегаты попадают в разделы Аналитика и Система. Отдельно ведется разрез по воркерам: функция usage_stats.set_worker помечает, кто из воркеров сколько израсходовал.

    Проверка доступности¶

    Функция healthcheck() выполняет короткий вызов create без режима JSON. Параметр max_tokens равен 16, потому что рассуждающие модели тратят бюджет ответа на цепочку рассуждений. Тайм-аут составляет 20 секунд в эндпоинте /api/health/full и 30 секунд в /api/settings/test. Пустой llm_base_url дает явную ошибку «LLM не настроен».

    Эмбеддинги и подбор правил¶

    Модуль rag.py подбирает правила гайда под конкретный фрагмент текста. Он нужен, когда гайд большой и все правила не помещаются в промпт.

    Механика работы описана пунктами ниже.

    • Используется отдельный совместимый с OpenAI endpoint эмбеддингов (embedding_base_url, embedding_api_key, embedding_model) и пакет openai в синхронном варианте клиента OpenAI. Запросы идут батчами по EMBED_BATCH_SIZE, равному 90, с тайм-аутом EMBED_TIMEOUT в 20 секунд.
    • Индекс хранится в памяти по каждому гайду, ключом служит идентификатор гайда, а перестройка выполняется по content_hash. Правила превращаются в документы-подложки: заголовок, формулировка, обобщение и примеры. Близость считается косинусным расстоянием на numpy; внешних векторных хранилищ нет, потому что правил в гайде десятки.
    • Функция ensure_index(guide) вызывается в начале конвейера и прогревает индекс. Отдельный healthcheck() для эмбеддингов светится строкой Эмбеддинги в /api/health/full.
    • Метод retrieve(query, guide, task, k) складывает семантические скоры (_semantic_scores) с лексическими (_lexical_scores, по токенам) и надбавкой по метаданным (_metadata_boost: категория и область применения правила). Гибридная схема и есть то, что интерфейс показывает как статус гибридный в карточке гайда.
    • Без доступного endpoint эмбеддингов retrieve отдает все правила гайда. Это лексический или полный режим, в статусе он обозначен как lexical_only. На маленьких гайдах деградация безвредна, на больших точность подбора падает, но работа продолжается.

    Переменная RAG_CONFIG_VERSION версионирует схему кэша индексов, чтобы смена формата не подмешивала устаревшие векторы.

    Роль подбора в конвейере¶

    Конвейер v2 вызывает _retrieve_batch для фрагментов и _retrieve_one для стадий терминологии и согласованности. Подобранное множество правил (top-k) подставляется в промпт воркера, поэтому модель проверяет не «вообще все нормы», а релевантные этому фрагменту.

    Диагностику подбора дают поля meta.retrieval.rule_hit_counts и rules_never_offered. Правило, которое не предложил ни один запрос, это плохой признак: сформулировано оно так, что эмбеддинг его не находит, и фактически проверка его не выполняет. Порядок формулировок правил описан на странице Правила Style Guide в коде.
