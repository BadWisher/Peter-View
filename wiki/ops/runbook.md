# Дежурство по авариям

Пошаговые рецепты для типовых инцидентов. Диагностика в общем [Мониторинг](monitor.md), статус-страница в [Системе](../users/system-status.md).

## Сервис лёг

```bash
docker compose ps           # что упало/перезапускается
docker compose logs --tail=200 backend
```

| Статус контейнера | Что делать |
|---|---|
| `Restarting (137)` backend | OOM. `mem_limit 2g`, скорее всего разрослись снимки watch или большой документ с LLM. Временно: поднять лимит в compose-override, затем разобраться |
| `unhealthy` backend | `/api/health` не отвечает. Смотрите лог на трейсы запуска; чините рестартом `docker compose restart backend` |
| `unhealthy` languagetool | JVM не стартует/падает. `docker compose logs languagetool`; частые причины конец RAM, повредившийся том |
| frontend `unhealthy`, backend healthy | nginx не может достучаться до backend или бэкенд грузится. Прокси возвращает 502, сервис «оживёт» |

После любого вмешательства: `curl -s localhost:3080/api/health` и одна контрольная проверка текста во «Вычитке».

## Данные повреждены или удалены

Главный инстинкт: не чинить на живом томе. Остановить стек (`make down`), восстановить из снапшота по [инструкции](backup.md), поднять, проверить «Систему». Если снапшот не свежий, потерянные часы данных это цена; после восстановления добавьте алерт на возраст бэкапа в [Мониторинге](monitor.md).

Никогда не `docker compose down -v` на проде: флаг `-v` удаляет тома вместе с `backend-data`.

## Забыт пароль последнего админа

При пустом списке пользователей сервис пересоздаёт `admin/admin` на старте. Порядок:

1. `make down` (без `-v`).
2. Резервная копия тома на всякий: скопировать `/var/lib/docker/volumes/..._backend-data/_data/users.json`.
3. Удалить только запись `admin` из `users.json` (или весь файл, если готовы сбросить пароли всем).
4. `./deploy.sh`, войти `admin/admin`, немедленно сменить пароль.

## Сессии слетают каждые несколько минут

Backend перезапускается. `docker inspect <backend>` поле `RestartCount`, `dmesg | grep -i "killed process"` на OOM. Пока причина не найдена, пользователи будут жаловаться на «выкидывает». Сессии в памяти это архитектурное ограничение единственного инстанса, лечить нечем, кроме как устранить сам рестарт-цикл.

## Проверки медленно деградируют

Признаки: задачи упираются в 900-секундный таймаут, воркеры в ретраях.

1. «Система» → LLM: растёт latency у провайдера?
2. Диск: `/app/data` переполнен? SQLite-запись тормозит всю очередь.
3. `docker stats` параллельно с нагрузкой: CPU backend упирается в 100% (Vale + pymorphy3 синхронные куски)?
4. `LLM_CONCURRENCY` слишком высок для тарифа провайдера → очередь на 429-ответах, ретраи занимают слоты. Понизить.

## Вжарка под нагрузкой

Формальные проверки обслуживаются семафором на 3 одновременных `check_text` (кроме того 3 LLM-проверки могут стоять в очереди). Это штатное поведение, а не авария: пользователь видит очередь в прогресс-баре, задача не падает. Если очередь систематическая, поднимайте параллельность осознанно и наблюдайте за памятью.

## Аварийное отключение разделов

Выключить небезопасный/нагрузочный раздел можно только правкой `.env` (`FEATURE_*=false`) и рестартом backend (сессии слетят, предупредите). На время разбора инцидента это оправданно: API закрытых разделов начинает отвечать 404 на уровне middleware.

## Эскалация и отчёт

После любого инцидента сохраните: вывод `docker compose ps`, последние ~500 строк логов backend/LT, скрин «Системы», время начала/конца. Полезно для отката и для баг-репортов в репозиторий (приватный security-инцидент по [SECURITY.md](https://github.com/BadWisher/Peter-View/blob/main/SECURITY.md), не публичный issue).
