# Мониторинг работы сервиса

Штатных метрик Prometheus у сервиса нет. Есть три канала наблюдения: health-эндпоинты, логи контейнеров и встроенная страница «Система».

## Health-эндпоинты

| Эндпоинт | Кто отвечает | Смысл |
|---|---|---|
| `GET /api/health` (наружу через nginx, без авторизации) | backend | `{status: ok, version}` живой ли процесс |
| `/` (порт 3080) | nginx | стек поднят и проксирует |
| `http://languagetool:8010/v2/languages` | внутренний LT | доступна ли формальная проверка (изнутри сети docker) |
| `/api/health/full` (admin, cookie) | backend | LLM/эмбеддинги/диск/бэкап в одном JSON |

Простейший watchdog с хоста:

```bash
while true; do
  curl -fsS --max-time 5 http://localhost:3080/api/health >/dev/null || \
    notify-send "Peter View лежит"
  sleep 60
done
```

`/api/health/full` дёргает саму модель и endpoint эмбеддингов (по 20 с на запрос) и всегда отвечает 200, даже когда компоненты падают статус каждого в JSON. Не используйте его как liveness-пробу (тяжёлый, требует авторизации), это диагностика.

## Контейнерные healthcheck'и

Docker сам знает про здоровье: backend (`/api/health`, 10×12), frontend (`/`, 10×6), languagetool (`/v2/languages`, 15×20, start_period 90). `docker compose ps` покажет `healthy`/`unhealthy`; в `unhealthy` контейнер продолжает жить, но `depends_on: service_healthy` блокирует старт зависимых. Для оркестраторов и алертов мониторьте именно статус health, не наличие процесса.

## Логи

```bash
make logs                      # все три сервиса, follow
docker compose logs -f backend # только приложение
```

Формат лога backend: `%(asctime)s %(name)s %(levelname)s %(message)s`, уровень INFO. Полезные фильтры:

- `grep -i "llm\|v2-воркер"` запросы к модели и ретраи стадий;
- `grep -i backup` цикл резервного копирования;
- `grep -i "SSRF\|не удалось разрешить"` попытки загрузки запрещённых адресов;
- `WARNING.*регулярное выражение` таймауты пользовательских regex (200 мс на строку).

Ротация docker json-file: 10 МБ × 3 файла на сервис (~30 МБ максимум на контейнер). Долгосрочного хранения логов нет; если нужен аудит дольше последней тысячи строк, шейпите `docker logs` в свою коллектор-систему.

## Что ломается первым и как это выглядит

| Канал | Признак проблемы |
|---|---|
| Диск | «Система» жёлтая/красная; ошибки записи истории; бэкапы не пишутся. Порог тревоги: свободно < 2 ГБ |
| Память backend | контейнер перезапускается (`restarts` в `docker inspect`), сессии слетают. `mem_limit 2g`, Chromium при снимках страниц ест память агрессивно |
| JVM LanguageTool | контейнер LT `unhealthy`, находок LT в отчётах нет. `mem_limit 1536m` при `Xmx 1g` запас 512 МБ на overhead |
| Модель | воркеры LLM в ошибке, жалобы пользователей на «пустые» отчёты. Смотрите `POST /api/settings/test` или кнопку в UI |
| Сеть провайдера | ретраи в логах, задачи приближаются к 900-секундному потолку |

## Внешний мониторинг, которого нет (и чем закрыть)

Сервис не светит метриками. Практичный минимум для дежурного:

1. `curl /api/health` раз в минуту (доступен без авторизации).
2. `docker inspect -f '{{.State.Health.Status}} {{.RestartCount}}'` по трём контейнерам раз в 5 минут.
3. `df` на разделе тома `backend-data` и на `./backups` раз в 10 минут.
4. Возраст последнего `peterview-*.tar.gz` больше 24 часов алерт.
