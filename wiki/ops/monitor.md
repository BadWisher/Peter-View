# Наблюдение за работой сервиса

Эта страница описывает каналы наблюдения за развернутым сервисом. Она нужна
администратору и дежурному, которые хотят понять, жив ли сервис и где узкое
место.

Штатных метрик Prometheus у сервиса нет. Наблюдение идет по трем каналам:
health-эндпоинты, логи контейнеров и встроенная страница **Система**. Страница
отвечает на вопросы: какой эндпоинт за что отвечает, как читать логи, что ломается
первым и какой минимум забрать во внешний мониторинг.

## Health-эндпоинты

Доступность сервиса проверяют эндпоинтами из таблицы.

| Эндпоинт | Кто отвечает | Смысл |
|---|---|---|
| `GET /api/health` (наружу через nginx, без авторизации) | backend | жив ли процесс; возвращает `{"status":"ok","version":"0.1.0"}` |
| `/` (порт 3080) | nginx контейнера frontend | стек поднят и проксирует |
| `http://languagetool:8010/v2/languages` | внутренний LanguageTool | доступна ли формальная проверка (только изнутри сети docker) |
| `GET /api/health/full` (роль администратора, по cookie) | backend | состояние модели, эмбеддингов, диска, репозитория и снимка в одном JSON |
| `GET /api/config` (без авторизации) | backend | версия, состояние флагов разделов, настроен ли OIDC, включен ли Swagger |

Путь `/api/health/full` опрашивает саму модель и эндпоинт эмбеддингов (по 20
секунд на запрос) и всегда отвечает кодом 200, даже когда компоненты падают.
Статус каждого компонента лежит в теле JSON. Для пробы живости этот путь не
подходит из-за веса и требования авторизации, он служит диагностикой.

Простейший watchdog на хосте выглядит так.

```bash
while true; do
  curl -fsS --max-time 5 http://localhost:3080/api/health >/dev/null || \
    echo "$(date) Peter View недоступен"
  sleep 60
done
```

## Проверки готовности контейнеров

Docker сам отслеживает здоровье контейнеров параметрами healthcheck из
compose-файла.

- backend: запрос к `/api/health`, интервал 10 с, 12 попыток, стартовая пауза 20 с;
- frontend: запрос к `/`, интервал 10 с, 6 попыток, стартовая пауза 5 с;
- languagetool: запрос к `/v2/languages`, интервал 15 с, 20 попыток, стартовая
  пауза 90 с, потому что JVM прогревается медленно.

Команда `docker compose ps` показывает статус `healthy` или `unhealthy`. В
статусе `unhealthy` контейнер продолжает работать, но зависимость
`depends_on: condition: service_healthy` блокирует старт зависимых. Для
внешних алертов мониторьте именно статус health, а не наличие процесса.

## Логи

Логи смотрят двумя командами.

```bash
make logs                      # все три сервиса, в режиме follow
docker compose logs -f backend # только приложение
```

Формат лога backend задан в `app/main.py` строкой
`logging.basicConfig(level=logging.INFO, ...)` и имеет вид
`%(asctime)s %(name)s %(levelname)s %(message)s`, уровень INFO. Полезные
фильтры перечислены ниже.

- Строки с подстрокой `llm` показывают запросы к модели и повторы стадий.
- Строки со словом `backup` показывают цикл резервного копирования.
- Строки с подстрокой `SSRF` и текстом про неразрешенный адрес показывают
  попытки загрузить запрещенные адреса.
- Уровень WARNING со словом `регулярное выражение` отмечает тайм-ауты
  пользовательских регулярных выражений (200 мс на строку).

Ротация логов настраивается драйвером json-file: 10 МиБ на файл, 3 файла на
сервис, то есть примерно 30 МиБ максимум на контейнер. Долгосрочного хранения
логов нет. Если нужен аудит глубже последних тысяч строк, направляйте вывод
`docker logs` во внешнюю систему сбора.

## Первичная диагностика по каналам

Таблица связывает канал наблюдения с признаком проблемы.

| Канал | Признак проблемы |
|---|---|
| Диск | страница **Система** становится желтой или красной, история перестает писаться, снимки не создаются; тревожный порог меньше 2 ГБ свободно |
| Память backend | контейнер перезапускается (поле `restarts` в `docker inspect`), сессии слетают; лимит 2 GiB, Chromium при снимках страниц расходует память агрессивно |
| JVM LanguageTool | контейнер в статусе `unhealthy`, находок LanguageTool в отчетах нет; лимит 1536 MiB при `Xmx 1g` оставляет 512 MiB на накладные расходы |
| Модель | воркеры в статусе ошибки, пользователи жалуются на пустые отчеты; проверьте кнопкой **Проверить подключение** или запросом к `/api/settings/test` |
| Сеть провайдера | повторы запросов в логах, задачи приближаются к потолку 900 с (`LLM_JOB_TIMEOUT`) |

## Минимум для внешнего мониторинга

Сторонний мониторинг забирает четыре показателя.

1. Опрос `GET /api/health` раз в минуту (эндпоинт доступен без авторизации).
2. Снятие состояния здоровья и счетчика перезапусков тремя контейнерами раз в
   5 минут:
   `docker inspect -f '{{.State.Health.Status}} {{.RestartCount}}'`.
3. Проверка свободного места на разделе тома `backend-data` и в каталоге
   `./backups` раз в 10 минут командой `df`.
4. Алерт, когда возраст последнего файла `peterview-*.tar.gz` превышает 24 часа.
