# Вход через OIDC (Keycloak, Entra, Okta)

Сервис умеет входить через OpenID Connect провайдера по коду авторизации. Пользователь видит на странице логина дополнительную кнопку, провайдер подтверждает личность, сервис заводит локальный аккаунт с ролью из групп токена.

## Конфигурация

Все переменные в `.env`, после изменения перезапуск:

```text
OIDC_ISSUER=https://sso.example.ru/realms/corp
OIDC_CLIENT_ID=peterview
OIDC_CLIENT_SECRET=<секрет клиента>
OIDC_REDIRECT_URI=https://peterview.example.ru/api/auth/oidc/callback
OIDC_ADMIN_GROUPS=docs-admins,platform-team
```

| Переменная | Смысл |
|---|---|
| `OIDC_ISSUER` | base-URL провайдера; discovery берётся с `{issuer}/.well-known/openid-configuration` |
| `OIDC_CLIENT_ID` | клиент, зарегистрированный у провайдера |
| `OIDC_CLIENT_SECRET` | секрет (для публичных клиентов можно оставить пустым, если провайдер разрешает flow без секрета) |
| `OIDC_REDIRECT_URI` | точный callback-адрес; регистрируйте его у провайдера слово в слово |
| `OIDC_ADMIN_GROUPS` | через запятую: имена групп/ролей, дающие админа |

Сервис считает OIDC настроенным, когда заданы `OIDC_ISSUER` и `OIDC_CLIENT_ID`; тогда фронт показывает кнопку входа. Прочие переменные должны быть заполнены до первого входа.

## Как проходит вход

1. Клик по кнопке `GET /api/auth/oidc/start`: сервис формирует ссылку авторизации с `state` и `nonce` (хранятся в памяти процесса 10 минут), редиректит на провайдера. Flow код-верификатор (PKCE) не используется.
2. Провайдер аутентифицирует, редиректит на callback с `code` и `state`.
3. Сервис меняет код на токены (проверка `state`/`nonce`), берёт userinfo, scope `openid profile email`.
4. Роль: `admin`, если хотя бы одна из групп/ролей пользователя (`groups`, `roles`, `realm_access.roles` в зависимости от провайдера) пересекается с `OIDC_ADMIN_GROUPS`; иначе `editor`.
5. Логин привязывается к username из токена; при первом входе создаётся локальная запись с пустым паролем и `source: oidc`.
6. Редирект на `/#/check` с выставленной сессионной cookie. Дальше сессия живёт по общим правилам (12 ч, слетает при рестарте backend).

## Поведение таких аккаунтов

- Локальный вход паролем для OIDC-аккаунта запрещён («Неверный логин или пароль» даже при верном пароле от прошлой локальной жизни).
- Смена пароля в UI для них скрыта, API отвечает «Пароль меняется у провайдера входа».
- Удаление пользователя в разделе «Пользователи» отвязывает его от сервиса локально; у провайдера ничего не меняется. При следующем входе аккаунт создастся заново.
- Отзыв доступа на стороне провайдера (убрали из групп) не выкидывает из активной сессии на 12 часов. Для мгновенного отзыва остаётся кнопка удаления аккаунта в «Пользователях» (она рвёт все сессии).

## Типичные проблемы

| Симптом | Причина и решение |
|---|---|
| «OIDC не настроен» на start | пустой `OIDC_ISSUER`/`OIDC_CLIENT_ID`, backend не перечитал `.env` |
| «Сессия входа устарела, попробуй снова» | прошло >10 минут с клика, либо backend перезапустился посреди флоу (pending-состояния в памяти) |
| Провайдер ругается на redirect_uri | строка в `OIDC_REDIRECT_URI` отличается от зарегистрированной; должен быть полный https-адрес наружного прокси, не `localhost:3080` |
| 400 «Провайдер не выдал токен» | неверный client secret, перепутан flow |
| Все OIDC-пользователи редакторы, хотя должны админы | имена групп не совпали с `OIDC_ADMIN_GROUPS` (регистр и префиксы важны; посмотрите payload токена на стороне провайдера) |
| Вход по http работает, по https нет | не выставлен корректный `X-Forwarded-Proto` на внешнем прокси; cookie Secure тогда отбрасывается |
