# Вход через OIDC

Эта страница описывает настройку входа через OpenID Connect. Она нужна
администратору, который подключает Peter View к корпоративному провайдеру
входа (Keycloak, Entra, Okta).

Сервис поддерживает вход по коду авторизации (authorization code flow).
Пользователь видит на странице входа дополнительную кнопку, провайдер
подтверждает личность, а сервис заводит локальную учетную запись с ролью,
полученной из групп токена. Страница отвечает на вопросы: какие переменные нужно
задать, как проходит вход, как себя ведут OIDC-учетные записи и как отлаживать
типовые отказы.

## Конфигурация

Все настройки OIDC читаются из `.env` и в интерфейсе не редактируются. После
изменения файла перезапустите стек.

```text
OIDC_ISSUER=https://sso.example.ru/realms/corp
OIDC_CLIENT_ID=peterview
OIDC_CLIENT_SECRET=<секрет клиента>
OIDC_REDIRECT_URI=https://peterview.example.ru/api/auth/oidc/callback
OIDC_ADMIN_GROUPS=docs-admins,platform-team
```

Назначение переменных показывает таблица.

| Переменная | Смысл |
|---|---|
| `OIDC_ISSUER` | базовый адрес провайдера; конфигурация обнаруживается по пути `{issuer}/.well-known/openid-configuration` |
| `OIDC_CLIENT_ID` | идентификатор клиента, зарегистрированного у провайдера |
| `OIDC_CLIENT_SECRET` | секрет клиента; для публичных клиентов можно оставить пустым, если провайдер разрешает flow без секрета |
| `OIDC_REDIRECT_URI` | точный адрес callback; регистрируйте у провайдера его слово в слово |
| `OIDC_ADMIN_GROUPS` | имена групп или ролей через запятую, которые дают роль администратора |

Сервис считает OIDC настроенным, когда заданы `OIDC_ISSUER` и `OIDC_CLIENT_ID`,
и только тогда фронтенд показывает кнопку входа. Остальные переменные должны
быть заполнены до первого входа.

## Как проходит вход

Последовательность шагов протокола выглядит так.

1. Пользователь нажимает кнопку, браузер обращается к `GET /api/auth/oidc/start`.
   Сервис формирует ссылку авторизации со значениями `state` и `nonce`
   (scope-запрос `openid profile email`), сохраняет пару в памяти процесса на
   600 секунд и редиректит на провайдера. Code-верификатор PKCE не используется.
2. Провайдер аутентифицирует пользователя и редиректит на callback с параметрами
   `code` и `state`.
3. Сервис проверяет `state` по памяти, меняет код на токены запросом к
   token-эндпоинту из discovery и получает userinfo.
4. Роль определяется по пересечению групп пользователя со значением
   `OIDC_ADMIN_GROUPS`. Сервис читает claims `groups`, `roles` и
   `realm_access.roles`, потому что провайдеры кладут группы по-разному. При
   пересечении роль `admin`, иначе `editor`.
5. Логин привязывается к username из токена (предпочтительно
   `preferred_username`, затем `email`, затем `sub`). При первом входе создается
   локальная запись с пустым паролем и источником `oidc`.
6. Браузер получает редирект на `/#/check` и сессионную cookie. Дальше сессия
   живет по общим правилам: 12 часов скользящего срока, сброс при перезапуске
   backend.

## Поведение OIDC-учетных записей

У учетных записей из OIDC четыре особенности.

- Локальный вход по паролю для такой записи запрещен. Интерфейс ответит «Неверный
  логин или пароль», даже если пароль от прошлой локальной жизни верный.
- Смена пароля в интерфейсе для них скрыта, а API отвечает, что пароль меняется у
  провайдера входа.
- Удаление пользователя в разделе **Пользователи** отвязывает его от сервиса
  локально; у провайдера ничего не меняется. При следующем входе через OIDC
  запись создастся заново.
- Отзыв доступа на стороне провайдера (например, удаление из группы) не
  прерывает активную сессию: она доживает свои 12 часов. Для мгновенного отзыва
  удаляйте запись в разделе **Пользователи**, удаление рвет все сессии
  пользователя.

## Миграция локальных учетных записей

Если у пользователя уже была локальная запись с тем же username, включение OIDC
меняет только путь входа. Чтобы перейти, пользователю достаточно войти через
кнопку OIDC: запись продолжит жить с прежней историей проверок и настройками,
роль будет пересчитана по группам провайдера при каждом входе. После перехода
пароль в записи больше не используется, и выдавать новый локальный пароль не
требуется.

## Отладка типовых отказов

Симптомы и причины собраны в таблице. Формулировки ошибок приведены дословно так,
как их возвращает сервис.

| Симптом | Причина и решение |
|---|---|
| «OIDC не настроен» на старте входа | пусты `OIDC_ISSUER` или `OIDC_CLIENT_ID`, либо backend не перечитал `.env` после правки; перезапустите стек |
| «Сессия входа устарела, попробуй снова» | с момента клика прошло больше 600 секунд, либо backend перезапустился посреди входа: ожидающие состояния живут только в памяти процесса |
| Провайдер отвергает redirect_uri | строка `OIDC_REDIRECT_URI` отличается от зарегистрированной; нужен полный https-адрес через внешний прокси, а не `localhost:3080` |
| 400 «Провайдер не выдал токен» | неверный `OIDC_CLIENT_SECRET` или перепутанный flow; проверьте настройки клиента у провайдера |
| «Провайдер не вернул имя пользователя» | в токене пусты и `preferred_username`, и `email`, и `sub`; настройте выдачу claims у провайдера |
| Все OIDC-пользователи получают роль редактора | имена групп не совпали с `OIDC_ADMIN_GROUPS`; регистр и префиксы значимы, посмотрите payload токена на стороне провайдера |
| Вход по http работает, по HTTPS нет | на внешнем прокси не настроен корректный HTTPS или не выставлен `PROOFREADER_COOKIE_SECURE=true`, и браузер отбрасывает cookie с флагом Secure |

## Ограничения схемы

Три ограничения приняты сознательно и зафиксированы на странице [**Проектные
решения**](../arch/decisions.md).

- PKCE не используется. Для серверного confidential-клиента с секретом это
  допустимо, но сценарий публичного клиента без секрета слабее.
- Ожидающие состояния входа (`state`, `nonce`) живут в памяти процесса. Балансировка
  на несколько копий backend без sticky-сессий невозможна, да и не поддерживается
  архитектурой одного хоста.
- Discovery-конфигурация провайдера кешируется в процессе навсегда до
  перезапуска. Если провайдер сменил ключи подписи, автоматического
  обновления эндпоинтов не происходит: перезапустите контейнер.
