# Жесткая настройка для публичного хоста

Эта страница содержит чек-лист жесткой настройки. Она нужна администратору,
который выводит Peter View в публичный доступ, то есть на хост с белым адресом,
откуда сервис виден не только внутренней сети.

Сервис запускается с дефолтами, рассчитанными на интранет и локальную работу. Для
публичного хоста этих дефолтов мало. Ниже собран обязательный минимум, за ним
модель угроз, перечень того, что не закрыто самой сборкой и решается снаружи, и
карта секретов.

## Обязательный минимум

Действия для публичного хоста перечислены по порядку.

1. Смените пароль учетной записи `admin`. Значение `admin/admin` известно всем,
   и до смены пароля любой, кто достучался до порта, становится администратором.
2. Поставьте TLS через внешний прокси и установите
   `PROOFREADER_COOKIE_SECURE=true`. Иначе сессия передается по сети открыто.
   Порядок настройки прокси описан на странице [**TLS и обратный прокси**](tls-proxy.md).
3. Установите `PROOFREADER_SSRF_ALLOW_PRIVATE=false`. На публичном хосте
   пользователи не должны направлять сервис на внутренние адреса и на
   облачное хранилище метаданных. Защита от доступа к метаданных вшита в код,
   но приватные сети по умолчанию разрешены, и этот флаг их закрывает.
4. Задайте явный `PROOFREADER_SECRET` либо сохраните сгенерированный файл
   `data/watch.db.key` в резервных копиях. Это ключ обфускации паролей и снимков
   в хранилище раздела **Наблюдение**. Без явного значения сервис генерирует
   ключ сам при первом запуске, и потеря ключа делает сохраненные пароли
   нерабочими.
5. Оставьте `PROOFREADER_DOCS=false`. Публичный Swagger не нужен, а отключить его
   через `.env` нельзя, потому что значение зашито в compose-файл. Подробности на
   странице [**Переменные окружения**](config-env.md).
6. Не включайте `FEATURE_WATCH` и `FEATURE_API` без необходимости. Каждый флаг
   добавляет путь, по которому сервис обращается наружу по пользовательскому
   адресу. Чем меньше включенных разделов, тем меньше поверхность.
7. Храните резервные копии в зашифрованном хранилище. В архиве лежат ключи API и
   bcrypt-хеши паролей. Об этом написано на странице [**Резервное копирование и
   восстановление**](backup.md).

## Модель угроз

Ниже описано, кто попадает в сервис и что может сделать.

**Кто попадает в сервис.** Вход выполняется логином и паролем либо через OIDC,
действует ограничение 5 попыток на 5 минут для пары IP и логин. Минимальная длина
пароля 8 символов без требований сложности. Для публичного инстанса это слабое
место: включайте OIDC или закрывайте вход IP-политикой на прокси.

**Что делает аутентифицированный редактор.** Он загружает файлы и адреса на
проверку (текст уходит в настроенную администратором модель), читает и
экспортирует отчеты, работает с общим репозиторием документов, где права доступа
по папкам не настроены. Роль редактора рассчитана на доверенных людей, а не на
случайных гостей.

**Защита от SSRF.** Все пользовательские адреса (проверка по ссылке, раздел
**Наблюдение**) проходят модуль `net_guard`: разрешены только схемы http и https,
резолвинг DNS блокирует loopback, link-local (включая адрес 169.254.169.254),
multicast и reserved-диапазоны, каждый редирект (до 5) перепроверяется, размер
тела ограничен 10 МиБ. Приватные сети по умолчанию разрешены и закрываются
флагом из пункта 3. **Не проходят проверку** адреса OIDC-провайдера, модели и
эмбеддингов (их задает доверенный администратор) и адрес LanguageTool.

**Защита от XSS в отображении находок.** Весь пользовательский текст экранируется,
подсветка строится по событийному потоку открытых и закрытых меток. Для
сохраненных копий страниц действует отдельная защита: `<iframe sandbox>` и CSP
со значением `script-src 'none'`.

**Сессии.** Cookie `proofreader_session` имеет флаги HttpOnly и SameSite=Lax,
живет 12 часов скользящего срока. Защита от CSRF построена сверкой Origin или
Referer с заголовком Host, а не токеном. На нестандартных прокси с переписанным
`Host` возможны ложные ответы 403. Global-редиректа на 401 нет: просроченную
сессию интерфейс показывает ошибкой. Механизмы подробно разобраны на странице
[**Механизмы защиты**](../arch/security.md).

## Что не закрыто самой сборкой

Некоторые вещи сервис не делает, и их решают на площадке.

| Ограничение сборки | Решение на площадке |
|---|---|
| Нет ограничения частоты запросов по IP на nginx (брутфорс API после входа не лимитирован) | `limit_req` на внешнем прокси |
| Нет заголовка HSTS | `add_header Strict-Transport-Security` на внешнем TLS-прокси |
| Бинарь Vale в Dockerfile фактически не проверяется по sha256 (комментарий обещает проверку, кода сравнения нет) | закрепляйте итоговый образ по digest после ревью, не собирайте из непроверенных форков |
| Базовые образы закреплены по digest, но Dependabot отслеживает только pip | отдельно обновляйте digest образы, иначе они тихо устаревают |
| Логи 30 МиБ на сервис без внешней агрегации | внешний сбор логов, если нужен forensic-след длиннее этого |
| Мост корпоративного прокси `172.17.0.1:3128` без аутентификации | запретите вход на порт 3128 извне docker-сети брандмауэром, поднимайте мост только на VDI |

## Карта секретов

Таблица показывает, где лежит каждый секрет и с какими правами.

| Секрет | Место | Права и защита |
|---|---|---|
| Пароли (bcrypt) | `data/users.json` | том `backend-data`; файл внутри контейнера доступен на чтение всем (0644 по umask) |
| Ключи API модели и эмбеддингов | `data/llm_settings.json` | права 0600, маскируются в API: наружу уходит пустая строка и флаг **Ключ задан** |
| Пароли групп раздела **Наблюдение** | `data/watch.db` | обфускация ключом из `PROOFREADER_SECRET` (или сгенерированным и сохраненным в `data/watch.db.key`); это XOR-обфускация, а не криптографическая защита |
| `OIDC_CLIENT_SECRET` и `LLM_API_KEY` в `.env` | каталог репозитория на хосте | держите `chmod 600 .env`, не коммитьте `.env` |
