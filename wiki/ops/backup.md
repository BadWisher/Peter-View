# Резервное копирование и восстановление

Эта страница описывает, как создаются и восстанавливаются снимки данных сервиса.
Она нужна администратору, который отвечает за сохранность пользователей, гайдов и
истории проверок.

Все постоянные данные сервиса лежат в одном месте: в томе `backend-data`
(внутри контейнера путь `/app/data`) и в примонтированном рядом каталоге
`./backups`. Резервная копия представляет собой архив tar.gz всего каталога
`/app/data`. Дробных выгрузок по частям нет: пользователи, гайды, задачи и
снимки мониторинга архивируются вместе.

## Состав снимка

В архив попадает каталог `data/` целиком, за исключением самого каталога резервных
копий (фильтр в `backups.py` не пускает его в снимок, чтобы рекурсия не
раздувала архив). Перечислим содержимое.

- `users.json` с хешами паролей;
- `llm_settings.json` с ключами API (права 0600);
- `rules.json` и `user_prefs.json`;
- `styleguides/` со всеми пользовательскими гайдами;
- `repo/` с репозиторием документов (файлы размером до 25 МиБ каждый);
- базы `jobs.db` и `watch.db` в формате SQLite;
- `stats.db` со статистикой расхода токенов и истории проверок;
- `audit.jsonl` с журналом аудита.

Образы контейнеров в архив не входят: они воспроизводятся сборкой из репозитория
или забираются из реестра GHCR. Подробную структуру каталога данных описывает
страница [**Хранилище данных**](../arch/data-model.md).

## Автоматические снимки

Фоновый цикл в модуле `app/routers/background.py` просыпается каждые 6 часов и
проверяет возраст последнего снимка. Если последний снимок старше 12 часов,
цикл пишет новый. Практический смысл: сервис создает снимок не реже одного раза
в сутки, а интервал 12 часов в условии функции `needs_snapshot_today` дает
два шанса за сутки.

Файл получает имя вида `peterview-YYYYmmdd-HHMMSS.tar.gz`, права 0600 и кладется
в `BACKUP_DIR` (по умолчанию `/app/backups`, что на хосте соответствует
`./backups`). Ротация оставляет последние `BACKUP_KEEP` файлов (по умолчанию 7)
и удаляет более старые. Ротация видит только файлы вида `peterview-*`.

Проверить работу цикла можно так:

```bash
ls -la ./backups
```

Если снимков нет больше суток, фоновый цикл не запускался или падал. Смотрите
логи командой `docker compose logs backend | grep -i backup`.

## Ручной снимок

Ручной снимок создается командой Makefile.

```bash
make backup
```

Команда выполняет `docker compose exec backend tar czf ...` и пишет файл
`./backups/manual-<время>.tgz`. Учтите две особенности ручной команды.

1. Ручной снимок содержит тот же каталог `/app/data`, что и автоматический, и
   создается тем же tar без остановок контейнера (о нюансах целостности читайте в
   разделе **Целостность горячего снимка**).
2. Ротация знает только про префикс `peterview-`, поэтому файлы `manual-*`
   автоматически не удаляются никогда. Следите за ростом каталога `./backups`
   сами или чистите его вручную.

Перед каждым обновлением версии имеет смысл сделать ручной снимок и убедиться,
что автоматический свежий (см. страницу [**Обновление версии**](upgrade.md)).

## Целостность горячего снимка

Снимок делается на живой системе, контейнер при этом не останавливается. Для
JSON-файлов и журнала аудита это безопасно, но базы SQLite пишутся иначе.
Архив `tar.gz` не содержит контрольной суммы, и сервис не проверяет ее
автоматически.

Подстрахуйтесь двумя простыми действиями.

1. Сохраните отдельную копию снимка с датой в имени и сверьте размер файла
   (`ls -l`). Нулевой или подозрительно маленький архив признак того, что
   запись прервалась: в коде `make_snapshot` при ошибке удаляет недописанный
   файл, поэтому пустой файл в каталоге означает обходной путь записи.
2. Периодически проверяйте снимок на восстановление на тестовом окружении
   (раздел **Порядок восстановления** ниже). Проверенный снимок это единственный
   снимок, которому стоит доверять.

## Порядок восстановления

Проверенный пошаговый порядок описан ниже.

1. Остановите стек командой `make down`. Не используйте `down -v`, иначе удалите
   том вместе с последними данными.
2. Разархивируйте снимок в каталог данных тома. Именованный том volume лежит на
   хосте в `/var/lib/docker/volumes/<проект>_backend-data/_data`, но работать
   с ним напрямую неудобно. Проще поднять контейнер с подмененной точкой входа и
   разархивировать архив внутрь `/app/data`.

   ```bash
   docker compose run --rm --entrypoint sh backend -c \
     'rm -rf /app/data/* && tar xzf /app/backups/peterview-XXXXXXXX-XXXXXX.tar.gz -C /app/data'
   ```

   Файл снимка должен быть виден внутри контейнера: каталог `./backups`
   примонтирован как `/app/backups`.
3. Поднимите стек командой `./deploy.sh`.
4. Проверьте результат: вход администратором, наличие гайдов и истории проверок.

После восстановления все пользователи перелогинятся. Активные сессии живут в
памяти процесса и на диске не хранятся, поэтому после перезапуска их нет.

## Хранение снимков и защита секретов

Правила размещения архивов важнее самих архивов.

- Каталог `./backups` на том же диске, что и том `backend-data`, резервной
  копией не считается: при отказе диска теряются и данные, и копия. Копируйте
  снимки на другой хост средствами `rclone`, `rsync` или cron.
- В архиве лежат ключи API и хеши паролей. Кеши паролей представлены bcrypt, но
  сам файл снимка содержит настройки в открытом виде. Файл получает права 0600
  внутри тома, но при копировании в объектное хранилище права не переносятся.
  Шифруйте и канал передачи, и хранилище.
