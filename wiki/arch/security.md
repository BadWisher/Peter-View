# Механизмы защиты

Эта страница описывает, как устроена защита сервиса на уровне кода. Она нужна
тем, кто читает исходники, оценивает безопасность развертывания или настраивает
сервис для публичного доступа. Здесь приведены механизмы аутентификации,
защиты от CSRF, CORS, SSRF и межсайтового выполнения скриптов, обращение с
секретами, перечень публичных эндпоинтов и журнал аудита.

Страница объясняет устройство механизмов. Готовый чек-лист настроек для
публичного хоста находится в **Implementation Guide** на странице **Жесткая
настройка для публичного хоста**, а обоснования выборов записаны в
проектных решениях этой же страницы-раздела.

## Аутентификация и сессии

Аутентификация опирается на перечисленные ниже механизмы.

- Локальные пароли хранятся хешами bcrypt (стоимость по умолчанию библиотеки)
  в файле `data/users.json`. Минимальная длина пароля 8 символов, проверка
  сложности отсутствует.
- Сессия это токен `secrets.token_urlsafe(32)` в словаре `SESSIONS` памяти
  процесса. Cookie `proofreader_session` ставится с атрибутами HttpOnly,
  SameSite=Lax и Secure по флагу окружения. Время жизни 12 часов со
  скольжением: каждый запрос продлевает его. Рестарт процесса завершает все
  сессии.
- Против перебора работают два счетчика: 5 неудачных входов за 300 секунд на
  пару IP и логин и отдельно на IP. Счетчики живут в памяти и сбрасываются
  рестартом. Ответ отдается кодом 429 с русским сообщением. Смена пароля
  защищена этим же ограничителем.
- Вход через OIDC использует authorization code flow с параметрами state и
  nonce (время жизни 10 минут, в памяти процесса), без PKCE. Роль
  определяется пересечением групп из токена со списком `OIDC_ADMIN_GROUPS`.

## Защита от межсайтовых запросов

Токенов CSRF нет, схема строится на cookie и проверке происхождения. Middleware
обрабатывает все небезопасные методы (POST, PUT, PATCH, DELETE): если запрос
принес заголовок `Origin` или `Referer`, их хост сравнивается с `Host` запроса.
При несовпадении и отсутствии origin в `PROOFREADER_CORS_ORIGINS` ответ это код
403 с сообщением «Перекрёстный запрос отклонён». Запрос без заголовков Origin и
Referer проходит, потому что так ведут себя не-браузерные клиенты вроде curl.
Это осознанное послабление. Атрибут SameSite=Lax дополняет картину, потому что
кросс-доменные POST из чужих форм cookie не получат.

Обратный прокси обязан корректно пробрасывать
`Host`,
иначе собственные запросы интерфейса начнут получать 403.

## CORS

Политика CORS по умолчанию выключена: список разрешенных источников пуст, и
работа идет в режиме одного источника. Включение выполняется переменной
`PROOFREADER_CORS_ORIGINS` со списком точных источников. Значение `*` не
допускается, потому что несовместимо с передачей учетных данных. Механизм нужен
только когда интерфейс и API стоят на разных доменах.

## Защита от обращений к внутренним сервисам

Все адреса, которые указывают пользователи, проходят через модуль
`backend/app/net_guard.py`. Точки входа перечислены ниже: вычитка по URL
(`llm/documents.parse_url`), краулер `/api/check-url` (`crawler.safe_get`),
мониторинг (`watch_run.safe_request`) и извлечение текста из URL в служебных
модулях. Алгоритм состоит из четырех шагов.

1. Схема адреса строго http или https, хост непустой.
2. До соединения выполняется DNS-резолвинг, и каждый полученный адрес
   проверяется. Адреса loopback, link-local (включая 169.254.169.254 метаданные
   облачных платформ), multicast, unspecified и reserved блокируются всегда.
   Приватные диапазоны (10/8, 172.16/12, 192.168/16 и подобные) блокируются
   только при `PROOFREADER_SSRF_ALLOW_PRIVATE=false`; значение по умолчанию
   true рассчитано на интранет.
3. Редиректы не отдаются на откуп HTTP-клиенту: `follow_redirects=False`,
   каждый следующий адрес location проверяется тем же кодом, а их число
   ограничено `PROOFREADER_MAX_REDIRECTS` (5). Это закрывает класс атак, где
   публичный URL перенаправляет запрос на 169.254.169.254.
4. Размер тела ответа ограничен `PROOFREADER_MAX_FETCH_BYTES` (10 МиБ).

Из-под guard'а сознательно выведены обращения к OIDC-провайдеру (issuer,
token, userinfo), к конечным точкам модели и эмбеддингов и к LanguageTool. Эти
адреса выбирает администратор. Компрометация административного доступа означает
потерю контроля над всем сервисом при любой архитектуре, поэтому отдельного
реестра разрешенных адресов нет. При необходимости такой реестр добавляется, и
это известное ограниченное решение.

## CSP и заголовки nginx

Базовая политика содержимой страницы приведена ниже.

```text
default-src 'self'; script-src 'self'
```

Значение `unsafe-inline` и `unsafe-eval` для скриптов отсутствуют. Для стилей
`style-src` с unsafe-inline исключение сделано, потому что генерируемый
интерфейс использует inline-стили. Дополнительно заданы `object-src 'none'`,
`frame-ancestors 'none'`, `base-uri 'self'`, `form-action 'self'`. Вместе с
ними выдаются заголовки `X-Content-Type-Options: nosniff`,
`X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` и `Permissions-Policy`
с выключенными геолокацией, микрофоном и камерой.

В nginx настроены два исключения из общей политики, каждый по конкретной
нужде. Состав исключений описан ниже.

- `/api/docs` и `/api/redoc` разрешают CDN Swagger и ReDoc (jsDelivr,
  redoc.ly, gstatic), и только при включенном Swagger.
- `/api/watch/pages/*/copy` отдает сохраненные чужие страницы в iframe с
  ужесточенной политикой: `script-src 'none'`, `connect-src 'none'`,
  `object-src 'none'`, `form-action 'none'`, `base-uri https:`,
  `frame-ancestors 'self'`, `no-store`. На клиенте добавляется
  `<iframe sandbox="allow-same-origin allow-popups">`. Скрипты и формы
  выключены потому, что снимок это данные недоверенного сайта, отрендеренные
  внутри нашего источника.

## Отображение пользовательского текста

Все тексты пользователей (документ, сообщения правил, находки модели)
экранируются перед вставкой в HTML. Соответствие ведет функция `escapeHTML`
модуля `shared.js`, а разметка подсветки собирается событийным потоком
открывающих и закрывающих тегов, а не конкатенацией строк. Паттерны
пользовательских правил-regular expressions валидируются при сохранении
(некорректный паттерн код 400) и исполняются с бюджетом времени на строку.

## Обращение с секретами

Перечисленные ниже правила касаются ключей и паролей.

- API-ключи модели никогда не покидают сервер: `GET /api/settings` маскирует
  значения, а пустой PATCH не затирает сохраненное.
- Файл `llm_settings.json` пишется с правами 0600. Резервная копия каталога
  `data/` содержит ключи, поэтому архивы нужно хранить как секреты.
- Пароли порталов раздела **Наблюдение** скрыты потоком XOR по ключу
  `PROOFREADER_SECRET` (или автоматически сгенерированным `watch.db.key`).
  Это защита от случайного прочтения SQLite-файла, а не криптография в расчете
  на утечку всего тома.
- Файл `.env` исключен из git и содержит `OIDC_CLIENT_SECRET` и `LLM_API_KEY`.

## Публичные эндпоинты без сессии

Ниже перечислены эндпоинты, доступные без аутентификации.

- `GET /api/health`
- `GET /api/config`
- `POST /api/auth/login`
- `POST /api/auth/logout`
- `GET /api/auth/oidc/*`

Эндпоинт `/api/config` отдает версии, флаги разделов и два булевых признака
(наличие OIDC и Swagger). Это минимально необходимое для отрисовки страницы
входа. Все остальные эндпоинты требуют аутентификацию, а `/api/health/full`
требует дополнительно роль администратора.

## Журнал аудита

Файл `data/audit.jsonl` записывает события аудита: входы (успешные и неудачные),
выходы, создание и удаление пользователей, смену ролей и паролей, правки гайдов
и правил, смену настроек и запуск разделов. Хранится 2000 последних строк,
просмотр доступен в разделе **Система** администратору. В стандартной сборке
журнал никуда не отправляется: это файл на томе данных.
