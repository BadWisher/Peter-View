# Движки детерминированной проверки

Три движка плюс Python-реестр правил дают то, что сервис находит без обращения к модели: орфографию и пунктуацию, канцелярит, грамматические несогласования, запретные слова из лексикона. Их результаты уходят в LLM-конвейер как «кандидаты с доказательством», а в отчёте появляются с пометкой движка.

Фасад у всех один: `backend/app/checker.py` `check_text()`. Он гоняет движки параллельно, дедуплицирует находки и накладывает пользовательские регулярки. Конвейер v2 вызывает его через `evidence.collect_engine_evidence`.

## LanguageTool

`lt_client.py` клиент внешнего сервиса (`httpx`, не JVM-библиотека).

- Endpoint `LANGUAGETOOL_URL` (в compose `http://languagetool:8010/v2/check`), запрос form-urlencoded `text=<одна строка>`, `language=ru`. Таймаут клиента 30 с.
- Текст проверяется построчно: каждая строка отдельный запрос (параллельно, под семафором `MAX_CONCURRENT_REQUESTS`), чтобы LT не склеивал контекст между блоками. Строки короче 3 знаков пропускаются. Номера строк потом и есть привязка к блокам.
- Находка несёт `rule.id`, категорию, `offset/length`, `replacements`, контекст. `SKIP_RULES` (список id) и набор фильтров ложных срабатываний отбрасывают мусор: технические термин-леммы (`api`, `деплой`, `эндпоинт`…), дефисные склейки без пробела, отдельные пунктуационные правила на `.`/`,` в середине строки, легальные случаи многоточия («больше известного протокола»).
- Категории мапятся в уровень так: `TYPOS`/`SPELLING` Ошибка; `GRAMMAR`/`PUNCTUATION` Замечание; `STYLE`/`TYPOGRAPHY` Совет; неизвестная категория Замечание.
- Ошибки surfacing: недоступный LT (любое исключение сети) даёт пустой список и предупреждение в логе; проверка без LT всё равно завершается, просто без его сигналов.

## Vale

`vale_runner.py` обёртка над бинарём Vale (стилевой линтер для prose). Конфиги стилей в `backend/vale/`, базовый свод норм на русском.

- Текст пишется во временный файл, Vale запускается как subprocess с `--output=JSON`, stdout парсится в находки.
- Каждая находка Vale несёт `Check` (имя правила), `Message`, `Severity` (Vale использует error/warning/suggestion), `Span`.
- `vale_runner` транслирует severity в нашу шкалу и пробрасывает `rule_id`, который реестр правил связывает с человекомочитаемым описанием. Vale хорош там, где нужна жёсткая текстовая норма, повторяемая от документа к документу (запрет длинного тире, «не начинайте с „Таким образом“»).

## Морфологические проверки

`custom_checks.py` набор Python-проверок на `pymorphy3` (морфологический разбор) и `razdel` (сегментация предложений), возвращает список `Issue`. Всего в модуле шесть функций, `run_all_custom_checks` вызывает пять:

- `check_passive_voice` страдательные конструкции («был разработан»). Функция определена, но в `run_all_custom_checks` не подключена мёртвый код на сегодня;
- `check_anthropomorphism` одушевление неживого («модуль понимает», «сервис знает»);
- `check_sentence_length` слишком длинные предложения (счёт слов в предложении);
- `check_formal_you` обращение: предписанное «Вы» с большой против случайного «ты»;
- `check_adj_noun_agreement` рассогласование прилагательного и существительного в падеже/роде;
- `check_subject_verb_agreement` рассогласование подлежащего и сказуемого.

Реализация: razdel дробит текст на предложения и токены, pymorphy3 даёт грамматические признаки, дальше декларативные предикаты. Результат finding с `rule`, текстом, рекомендацией и уровнем. Все три движка дают находки одного словарного формата, `checker.py` лишь обогащает их (`_enrich_issue`) и помечает источник: Vale и морфология `style-guide`, LanguageTool `spelling`.

## Реестр правил: три источника правды

В коде три разных свода, которые легко перепутать.

**1. `style_guide_registry.py` Python-реестр (~35 правил `RuStyleGuide.*`).** Обслуживает движковый слой. Каждая запись: `id`, `section`, `group`, `name`, формулировка `rule`, поле `engine` (`vale` или `llm`) и `automation` (`automatic`/`manual`), severity, good/bad примеры. `enabled_vale_rule_ids()` возвращает id правил с `engine: vale, automation != manual` именно этот whitelist applied к выводу Vale (`checker` кидает всё, чего нет в реестре-вайтлисте). `_enrich_issue` через `get_rule` обогащает находку секцией и именем правила для отчётов. UI `/api/rules/builtin` отдаёт весь реестр (`get_registry`).

**2. `backend/styleguide/rules.yaml` (формат v3, смонтирован read-only как `STYLEGUIDE_PATH`).** Из него сидится встроенный LLM-гайд «Базовый» (`styleguide_store.seed_default`), он же база для подбора правил моделью. Схема записи:

```yaml
- rule_id: RuStyleGuide.Glossary
  title: Глоссарий
  section: Ключевые рекомендации / Глоссарий
  group: Ключевые рекомендации
  rule: Использовать утвержденные термины из глоссария.
  severity: error                # error | warning (или suggestion)
  machine_verifiable: true       # находку движка можно не верифицировать моделью
  mandatory: false
  priority: 90
  scope: all                     # all | document | section | sentence | token
  relationships: {}              # conflicts: [rule_id, ...]
  good_examples: [...]
  bad_examples: [...]
```

Комментарий в самом начале файла обещает авто-перестройку RAG-индекса при смене содержимого (индекс keyed по content hash гайда, так что обещание выполняется).

**3. `BASE_RULES` (`llm/styleguide.py`) пять базовых правил** (`Базовая.Орфография`, `Пунктуация`, `Грамматика`, `Стиль`, `Форматирование`). Они всегда валидны для модели: `effective_ids = id|ы гайда | BASE_IDS | id-ы лексикона`. Смысл: полная LLM-проверка не использует LanguageTool (грамматика на строках это работа движка, модель дороже), поэтому базовую грамотность в LLM-отчёте ловит сама модель по этим пяти правилам.

Ключевые поля для конвейера:

- `machine_verifiable: true` движок находит такую норму объективно, кандидат от движка идёт в итог без верификатора;
- `relationships.conflicts` и `conflict_family` участвуют в разрешении противоречий ([Конвейер](pipeline.md)): два взаимоисключающих правила не могут дать две правки одного места;
- `priority` + `mandatory` + `scope` образуют ключ приоритета (`rule_precedence_key`), по которому конфликтующие правила ранжируются.

Глобальные пользовательские регулярки (`routers/rules.py`, `data/rules.json`) накладываются в `checker.check_text` после движков: паттерн до 500 знаков, движок `regex` с микро-таймаутом на строку (`USER_REGEX_TIMEOUT_MS`, по умолчанию 200 мс), чтобы катастрофический бэктрекинг не подвесил процесс.

## Как сигналы движков попадают в LLM-отчёт

`evidence.collect_engine_evidence` один раз прогоняет `check_text` по тексту, где каждый блок одна строка (так находку легко привязать к `block_index`; колонки внутри строки при этом сохраняются). Для каждого finding:

1. `rule_id` берётся из `registry_id` (для LT-находок он нормализуется в `Базовая.Орфография`).
2. Находка оставляется, только если её `rule_id` входит в `guide.effective_ids` правило реально есть в текущем гайде, в базовом наборе или в лексиконе. Иначе отбрасывается: движок нашёл, но по норме, которую этот гайд не декларирует.
3. Формируется кандидат формата модели: `evidence_source: engine`, `verification_required: not machine_verifiable`; severity конвертируется в домен модели (error→blocker, warning→suggestion, suggestion→minor).

`collect_lexicon_evidence` отдельно ищет точные вхождения запрещённых терминов гайда (`lexicon_forbidden`) регэкспом с границами слова, и порождает кандидатов с пометкой, что это лексикон, а не модель. Такие кандидаты помечаются на верификацию (модель должна проверить контекст: «экран» в «экран импорта»).

**Смысл разделения.** Детерминированные сигналы дают покрытию надёжность (не галлюцинируют, воспроизводимы), а LLM-стадии глубину (смысл, следование формулировкам правил). Верификатор не даёт модели выдумывать поверх движков, а фильтр по `effective_ids` не даёт движкам находить то, чего в гайде нет.
