# Архитектура: обзор

Peter View это веб-сервис проверки текстов на русском. Текст проходит два класса проверок: детерминированные движки (грамматика, стиль, морфология) и языковую модель (смысл, следование стилевому гайду, согласованность терминов). Модель не решает сама: её находки проходит верификатор, отрезающий правки без ссылки на конкретное правило и без реального вхождения в текст.

## HLD: крупные блоки

```text
браузер (SPA, vanilla JS, без сборки)
    │  http(s)
    ▼
frontend-контейнер (nginx)
    │  статика + reverse proxy /api/ → backend:8000
    ▼
backend (FastAPI, один процесс, asyncio)
    ├── routers/        HTTP-слой: 89 маршрутов, роли, флаги разделов
    ├── checker.py      фасад детерминированных движков
    │     ├── lt_client.py        → контейнер LanguageTool (JVM, ru)
    │     ├── vale_runner.py      → бинарь Vale внутри backend
    │     ├── custom_checks.py    → pymorphy3 + razdel
    │     └── style_guide_registry.py + styleguide/rules.yaml
    ├── llm/            конвейер вычитки моделью
    │     ├── documents.py    разбор входов в блоки (docx/html/md/txt/url)
    │     ├── pipeline_v2.py  планировщик стадий (v1 для откатов)
    │     ├── workers.py      вызовы воркеров по jinja2-промптам
    │     ├── evidence.py     мост: сигналы движков → кандидаты той же схемы
    │     ├── client.py       OpenAI-совместимый HTTP-клиент, кэш, семфор
    │     └── jobs.py         очередь задач, SQLite jobs.db, SSE-стрим
    ├── подсистемы: repo_store (документы), api_specs (OpenAPI), watch_* (мониторинг), shot_templates
    └── данные: /app/data (JSON + SQLite) на томе backend-data; бэкапы в ./backups

languagetool-контейнер (JVM, только внутренняя сеть docker)
внешние зависимости: LLM endpoint и OIDC provider (задаёт админ)
```

Развёртывание один хост, три контейнера, наружу опубликован только порт nginx. Детали compose и образов [Стек](../ops/stack.md).

## Главный поток данных (проверка)

1. Браузер шлёт `POST /api/jobs` (multipart: `text`/`file`/`url`, `styleguide_id`, три флага групп, опциональная `prompt`). Ответ `{"job_id"}` мгновенный, работа уходит в asyncio-фон.
2. `documents.py` превращает вход в `Document`: список `Block` (абзац, заголовок, пункт, строка таблицы) с форматированием и стабильными индексами.
3. `pipeline_v2` режет блоки на чанки и по каждому поднимает нужных LLM-воркеров; параллельно `evidence.py` прогоняет детерминированные движки (`checker.check_text`) и сводит их вывод к той же схеме кандидата.
4. Кандидаты (LLM + движки + лексикон) дедуплицируются. Объективные находки (`machine_verifiable`) идут в итог без верификации, остальные пачками по 12 уходит верификатору: он принимает, отклоняет или понижает.
5. Разрешение конфликтов взаимоисключающих правил гайда, финальная дедупликация, простановка уровней Ошибка/Замечание/Совет, сборка отчёта.
6. Отчёт пишется в `jobs.db` и в историю; клиент получает прогресс по SSE `/api/jobs/{id}/stream` (события `start/delta/end/finished`) со страховочным поллингом `/api/jobs/{id}` раз в 1.2 с.

Путь «только движки, без модели» (`/api/check`, `/api/check-text`, `/api/check-url`) синхронный JSON/SSE-ответ из того же `checker.py`. UI на нём не работает (исторически), но он пригоден для интеграций и автотестов.

## Из ограничений архитектуры следуют свойства

- Один процесс, состояние в памяти: сессии, SSE-стримы, кэш клиента модели, OIDC pending. Рестарт выкидывает всех и рвёт незавершённые задачи (при старте они честно помечаются ошибкой «Прервано рестартом сервера»).
- Детерминированный checker обслуживает не больше 3 прогонов одновременно (semaphore), LLM-параллельность отдельная (`LLM_CONCURRENCY`).
- Модель внешний сервис: тексты пользователей уходят админски настроенному endpoint'у. Приватность = выбор endpoint'а и политика провайдера.
