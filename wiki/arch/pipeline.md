# Конвейер LLM-вычитки (v2)

Модуль `backend/app/llm/pipeline_v2.py`, входная функция `run_pipeline_v2(document, guide, progress, stream, options)`. Выбирается переменной `PIPELINE_VERSION` (по умолчанию `v2`, `v1` откат). Диспетчер `pipeline.run_pipeline` читает env, гоняет основную версию, при `PIPELINE_SHADOW=true` параллельно вторую и кладёт в `meta.shadow_comparison` числа `primary_only/secondary_only/shared` по хэгам находок `(block_index, rule_id, replacement)`. Это механизм метрик для сравнения версий, не режим работы.

Стадия, к которой относится воркер, проверяется дважды: по флагу UI (`options`: `language`/`styleguide`/`consistency`) и по env `PIPELINE_V2_STAGES` (список стадий через запятую). Соответствие стадий категориям UI:

| Стадия | Категория UI |
|---|---|
| language | Язык и ясность |
| evidence, guide, lexicon | Style Guide |
| structure, terminology, consistency | Термины и согласованность |

## Планирование

`_plan(len(blocks))` базовый размер чанка 8 блоков, перекрытие 2 (`chunking.DEFAULT_CHUNK_SIZE/DEFAULT_OVERLAP`); для длинных документов размер растёт до 28, чтобы число чанков не превысило `MAX_CHUNKS_TARGET=24`. Согласованность включается с `MIN_BLOCKS_FOR_CONSISTENCY` блоков, воркер согласованности ограничен `MAX_CONSISTENCY_BLOCKS=80` блоками (дальше документ сжимается).

Каждому чанку rules подбираются отдельно (`_retrieve_batch`, см. [клиент модели](model-client.md) про RAG): до 12 правил гайда для стадии guide, до 10 language-правил, до 12 structure. Терминологии и согласованности правила подбираются один раз на документ (top-28). Подбор и то, какие правила вообще предлагались воркерам, пишется в `meta.retrieval` (`rules_never_offered` правило, которое не увидел ни один воркер, сигнал недокрытия гайда).

## Воркеры

Имена из `WORKER_NAMES` (id в скобках, это же `source_workers` у кандидатов):

- **(0) Детерминированные сигналы** не LLM-вызов: результат `checker.check_text`, приведённый `evidence.py` к схеме кандидата, плюс точные попадания лексикона (`collect_lexicon_evidence`, id 8 в provenance). Привязка к блоку через «один блок одна строка» в `_engine_text`.
- **(1) Язык** проза чанка: ясность, канцелярит, сложные конструкции. Пропускается, если в чанке нет прозы (`_has_prose`).
- **(2) Структура** заголовки, списки, логика построения документа (`_has_structure`).
- **(4) Style Guide** сверка чанка с подобранными для него правилами гайда.
- **(5) Терминология** весь документ: единообразие названий, соответствие словарю.
- **(7) Согласованность** весь документ: противоречия между частями («в разделе 2 порт 8080, в разделе 5 9090»).
- **(6) Верификатор** финальный фильтр, см. ниже.

Контекст каждому чанковому воркеру окно ±6 блоков (`WINDOW_BLOCKS`), не весь документ (экономия токенов, кросс-ссылки задача терминологии/согласованности). Ответ воркера JSON-список кандидатов; валидация `schemas._clean_issue`:

- нет `rule_id` или id не из текущего гайда кандидат выкидывается (главный антигаллюцинационный фильтр);
- `severity` из домена `blocker/suggestion/minor`, иначе `suggestion`; маппинг в UI: `blocker→error(Ошибка)`, `suggestion→warning(Замечание)`, `minor→suggestion(Совет)`;
- `block_index` обязан существовать; `span_text` обязано буквально содержаться в тексте блока; правка, равная исходному тексту, не принимается.

## Надёжность проходов

Каждый вызов оборачивается `_retry_pass`: `asyncio.wait_for(PASS_TIMEOUT)` (env `PIPELINE_V2_PASS_TIMEOUT`, 360 с), при `LLMRequestError`/таймауте до `PASS_RETRIES` (2) повторов с экспоненциальной паузой (1, 2, 4... до 10 с). Не-LLM ошибки не ретраятся. Провалённый проход не вали задачу: воркер помечается `error` в стриме, остальные работают. Исключение: если вали вообще все воркеры и нет объективных сигналов движков, задача падает («Все v2-воркеры завершились ошибкой»).

## Верификатор и разбор конфликтов

Кандидаты объединяются (`_dedupe_candidates` по block_index+rule_id, provenance склеивается). Разделяются:

- `verification_required: false` (объективные движковые) приняты автоматически, статус `objective`;
- остальные сортируются (группировка по `group` правила, внутри по блоку, чтобы верификатор видел соседние кандидаты одного правила) и режутся батчами по `VERIFY_BATCH=12`. Каждым батчем воркер-верификатор получает блоки-контекст и выносит каждому кандидату вердикт (keep/reject/downgrade). Результат в `meta.verifier_outcomes`; отклонённые не попадают в итог, статистика `critic_dropped`.

Стадия `verifier` отключается env'ом (абляция для оценок): все непроверенные кандидаты проходят как есть с пометкой `ablation_unverified` и warning в метаданных. Для прода так делать не надо.

`_resolve_conflicts`: если два итоговых кандидата опираются на взаимоисключающие правила (`relationships.conflicts` или общий `conflict_family`), остаётся более приоритетный (`rule_precedence_key`: обязательность, приоритет, severity). Затем финальный `_dedupe` и `_build_report`.

## Отчёт

`_build_report` возвращает словарь (он же лежит в `jobs.report` и раздаётся `GET /api/jobs/{id}/report`):

```json
{
  "document": "источник",
  "styleguide": {"id": "...", "name": "..."},
  "summary": {"total": 0, "errors": 0, "warnings": 0, "suggestions": 0,
               "blocker": 0, "suggestion": 0, "minor": 0},
  "issues": [ {"block_index": 3, "rule_id": "...", "severity": "warning",
               "description": "...", "span_text": "...", "suggestion": "...",
               "engine": "Модель", "line": 4, "text": "...", "replacement": "..."} ],
  "blocks": [ {"index": 0, "type": "heading", "text": "...", "level": 2,
               "formatting": [...]} ],
  "pages_checked": 1,
  "partial": false,
  "meta": {"token_usage": {...}, "pipeline_version": "v2",
           "retrieval": {...}, "verifier_outcomes": [...],
           "conflicts": [...], "validation_rejections": [...]}
}
```

Фронтенд рисует левую панель по `blocks`, находки из `issues` навешивает на совпадения `span_text` (первое вхождение в блоке). Уровень наследуется: у движковых через severity маппинг `checker`'а, у модельных через `blocker/suggestion/minor`.

## v1: зачем оставлен

`pipeline.py` классический конвейер: воркеры 1–5,7,8 по каждому чанку, без разделения evidence/objective, меньше стадий подбора. Код общается с v2 общими хелперами (`_plan`, `_dedupe`, `_build_report`). Держится для мгновенного отката (`PIPELINE_VERSION=v1`) и как второй голос в shadow-режиме. Промпты v1 (`prompts/v1/*.jinja2`) и v2 (`prompts/v2/`) наборы разные; переключаются `PROMPT_VERSION`.
