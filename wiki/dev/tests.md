# Тесты и регрессия

Эта страница описывает три слоя проверок качества кода и порядок их запуска.
Она нужна разработчику, который меняет код и хочет понять, какие тесты его
защитят, и ревьюеру, который оценивает полноту изменений. Здесь приведены
команды запуска, состав unit-тестов, регрессионные кейсы правил, эталонный
оценочный прогон против живой модели, покрытие CI и перечисленные
пробелы в покрытии.

Страница отвечает на вопросы: что запускать после правки, какой тест поймает
ошибку в конкретной подсистеме и что вообще не покрыто автотестами.

Слои различаются ценой запуска. Быстрые unit-тесты на pytest выполняются на
хосте за секунды, 44 кейса регрессии правил требуют поднятого контейнера
backend и живого LanguageTool, а оценочный прогон обращается к реальной модели.
CI безусловно выполняет первые два слоя, третий запускается вручную.

## Команды запуска

Блок ниже показывает команды запуска всех слоев.

```bash
make test          # pytest -q из корня репозитория
make lint          # ruff (в CI выборка жестче: E9,F63,F7,F82)
make regression    # 44 кейса правил в контейнере backend (зависит от LanguageTool)
make ci-local      # lint + test + валидация compose + docker compose build
```

Конфигурация pytest находится в корневом `pyproject.toml`:
`pythonpath=["backend"]` и `testpaths=["backend/tests"]`. Поэтому запуск
выполняется из корня репозитория, а файла `conftest.py` нет. На хосте нужны
зависимости из `backend/requirements-dev.txt` (pytest, pytest-asyncio, ruff).
Внутри контейнера используется тот же механизм:
`docker compose exec backend python -m pytest`.

## Регрессия правил

Файл `backend/app/regression_checks.py` содержит 44 кейса вида «этот текст
должен дать именно эти правила и не должен дать вот эти». Пример кейса показан
ниже.

```python
RegressionCase(
    name="dash: en dash alone is not reported",
    text="Сервис – это компонент.",
    forbid_rules={"RuStyleGuide.Dash_EmDash"},
    forbid_texts={"–", "– (U+2013)"},
)
```

Поля `expect_rules`, `forbid_rules` и `forbid_texts` это множества,
заполняются по необходимости. Кейс говорит: на этом тексте правило должно
сработать (`expect_rules`) или не должно (`forbid_rules`), а запрещенные
подстроки (`forbid_texts`) не должны встретиться в фрагментах находок.

Прогон командой `python -m app.regression_checks` (функция `asyncio.run`)
прогоняет все кейсы через полный `check_text`, то есть заодно через живой
LanguageTool. Успешный результат выглядит как строка «Regression passed:
44 cases», при провале печатается список и возвращается код 1. Это же место,
куда добавляется кейс на каждое новое правило (шаг 5 процедуры на странице
[**Правила Style Guide в коде**](guides-rules.md)).

## Оценочный прогон против живой модели

Каталог `backend/eval/` содержит файл `cases.yaml` (версия 2) с 20 эталонными
документами и ожидаемыми находками по пяти способностям, а также `run_eval.py`
(483 строки) прогон через реальный конвейер с настроенной моделью. Пороги
приемки записаны в том же YAML и показаны в таблице ниже.

| Метрика | Порог |
|---|---|
| доля пройденных кейсов | не ниже 0.70 |
| полнота по правилам | не ниже 0.80 |
| полнота по блокам и span | не ниже 0.70 |
| полнота по подсказкам | не ниже 0.60 |
| нарушения из forbidden | 0 |
| clean-кейсы с ложными находками | 0 |
| полнота правил при k | не ниже 0.90 |
| полнота стадий finder и verifier | не ниже 0.80 |

Запуск выполняется командой `cd backend && python -m eval.run_eval` с
заполненными переменными `LLM_*`; форматы вывода JSON и JUnit. В CI прогон
отсутствует, потому что обращается к внешнему API и расходует деньги.
Практический смысл такой: прогоняйте до и после смены версии промптов, модели
или стадий конвейера, иначе «улучшение промпта» нечем измерить.

## Пробелы в покрытии

Ниже перечислено, что автотесты не проверяют. Синхронный слой checker
покрывается регрессией, но не отдельными unit-тестами по движкам: постфильтры
Vale и фильтры LanguageTool проверяются только сквозными прогонами. Краулер,
репозиторий документов и слой OpenAPI живут без отдельных тестов, их контракты
косвенно проверяются smoke-шагом CI.

## Smoke-проверка в CI

Файл `.github/workflows/ci.yml` запускается на pull request и push в main и
содержит две работы. Их состав описан ниже.

1. **lint-and-unit** на Python 3.12: компиляция всего дерева модулем
   `compileall`, `ruff check --select E9,F63,F7,F82` (детекторы сломанного
   кода, а не стиль), `pytest -q`.
2. **compose** полный стек на файле `.env` из примера: валидация трех
   compose-файлов, сборка, запуск в фоне, ожидание `/api/health` до 180 секунд,
   запросы корня и проверки здоровья, вход `admin/admin` в хранилище cookie и
   проверка отсутствия 5xx на шести GET-маршрутах, ожидание готовности
   LanguageTool, регрессия правил, дамп логов при провале и остановка со
   снятием томов в любом исходе.
