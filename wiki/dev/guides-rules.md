# Правила Style Guide в коде

Эта страница описывает, как правило Стайл гайда существует в коде сервиса.
Она нужна разработчику, который добавляет новое правило или правит формулировку
существующего. Здесь приведены карта трех представлений правила, поля записи
реестра, формат Vale-стиля, порядок генерации `rules.yaml`, устройство
промптов, назначение оценочного прогона и пошаговая процедура добавления
правила.

Страница отвечает на вопросы: в скольких местах править одно правило, что
произойдет при расхождении копий и чем проверить результат. Что такое гайд
глазами администратора описано в [**User Guide**](../users/quickstart.md) на странице [**Style Guide**](../users/styleguide.md),
путь кандидата через верификатор на странице [**Конвейер проверки моделью**](../arch/pipeline.md).

## Карта представлений

Правило стилистики существует в проекте в трех представлениях. Таблица ниже
показывает, кто каждое из них потребляет.

| Артефакт | Кто использует | Формат |
|---|---|---|
| `backend/vale/styles/RuStyleGuide/*.yml` (48 файлов) | Vale CLI | стили типов `existence`, `substitution`, `consistency` с сырыми регулярными выражениями в поле `raw` |
| `backend/app/style_guide_registry.py` (56 правил плюс слой LanguageTool) | `checker.py` для обогащения находок, модальное окно правил в интерфейсе, реестр для `effective_ids` | словари Python |
| `backend/styleguide/rules.yaml` (версия 3, те же 56 правил) | конвейер модели через подбор правил: тексты норм уходят в промпты | YAML |

Дублирование сознательное, потому что потребители разные: Vale понимает только
собственные YAML, модели нужен
человеческий текст правила с примерами, Python-слой держит метаданные: движок,
автоматизацию, приоритет и связи правил. Расхождение между реестром и
`rules.yaml` ловит тест `test_styleguide_consistency.py`: он сверяет
идентификаторы, строгости и поля. Поэтому порядок правки всегда один: сначала
реестр, затем перегенерация YAML, затем Vale-стиль.

## Поля записи реестра

Каждый элемент списка `RULES` в `style_guide_registry.py` устроен как словарь
ниже.

```python
{
  "id": "RuStyleGuide.Dash_EmDash",
  "section": "Пунктуация / Тире",
  "group": "Пунктуация",              # одна из 5 групп интерфейса
  "name": "Длинное тире",
  "rule": "Не использовать em-dash...",
  "generalization": "...",            # как применять, для модели
  "engine": "vale",                   # vale | python | manual
  "automation": "automatic",          # automatic | partial | manual
  "severity": "error",                # error | warning | suggestion
  "good_examples": ["..."], "bad_examples": ["..."],
  # служебные (для подбора правил и разрешения конфликтов):
  "categories": [...], "tasks": ["proofreading"], "scope": "all",
  "priority": 90,                     # error 90, warning 60, suggestion 40
  "machine_verifiable": True,         # находка не идет к верификатору
  "relationships": {"supersedes": [...]}, "conflict_family": "...",
  "constraints": {"forbidden_chars": ["—"], "required_chars": ["–"]},
}
```

Поле `constraints` не косметика. Модуль `llm/schemas.py` выбрасывает замечание
модели, если ее собственная правка нарушает ограничение правила: например,
модель предложила длинное тире там, где требуется среднее, или внесла букву ё в
слово из-под исключения.

Итоговые числа такие: 56 правил плюс запись `LanguageTool.ru` (орфографический
слой не является правилом, но лежит в реестре для единообразия интерфейса),
всего 57 записей. Распределение по полю `engine`: vale у 47 записей, python у
5, manual у 4, еще одна запись относится к LanguageTool. Автоматически из
vale-записей включаются 45 (условие `automation != manual`), функция
`style_guide_rule_ids` возвращает 52 идентификатора.

Группы правил для навигации в интерфейсе и их размер перечислены ниже.

- Ключевые рекомендации, 21 правило.
- Общие принципы, 12 правил.
- Язык и грамматика, 10 правил.
- Пунктуация, 8 правил.
- Форматирование, 5 правил.

## Формат Vale-стилей

Файл `.vale.ini` в каталоге `backend/vale` включает стиль `RuStyleGuide`.
Пример файла стиля стандартен для Vale и показан ниже.

```yaml
extends: existence
message: "Убедитесь, что аббревиатура расшифрована при первом использовании."
level: suggestion
nonword: true
raw:
  - '\b[А-ЯЁ]{2,}\b'
exceptions: [IP, URL, HTTP, ...]
```

Модуль `vale_runner.py` запускает бинарь с параметром `--output JSON` на
временном файле и забирает сообщения и позиции. После Vale идут
Python-постфильтры, потому что регулярные выражения Vale не различают контекст.
Типовые постфильтры приведены списком: единицы вида Мбит/с снимаются у правила
`Slash_Words`, слова «её», «ею», «всё», «все» снимаются у `LetterYo`,
латинские аббревиатуры в кавычках снимаются у `Quotes_LatinInQuotes`.
Постфильтр расширяет находку `Dash_EmDash` до уровня предложения и подставляет
замену на среднее тире.

Добавляя Vale-стиль, создайте и запись в реестре с тем же окончанием
идентификатора (`RuStyleGuide.<ИмяФайла>`). Без нее произойдут три вещи: обогатитель
`checker.py` не найдет метаданные, интерфейс покажет находку без имени правила, а
фильтрация по `effective_ids` в модуле `evidence.py` отбросит находку как
чужую.

## Файл rules.yaml и его генерация

Файл `styleguide/rules.yaml` перегенерируется из реестра скриптом
`styleguide/_generate.py`. Конвертация запускается вручную, поля берутся из
реестра, значение `version` поднимается при смене схемы. Файл примонтирован в
контейнер только для чтения и подхватывается без пересборки образа: индекс
подбора правил сравнивает хеш содержимого и перестраивается.

В рабочей установке администратор правит правила не в YAML, а через раздел
гайдов (API `/api/styleguides`). Встроенный набор копируется в
`data/styleguides/` загрузчиком `styleguide_store.seed_default()`,
пользовательские гайды живут рядом. Файл YAML это поставка «из коробки».

## Тексты промптов

Промпты Jinja2 лежат в `backend/app/llm/prompts/` в двух каталогах по версиям
конвейера. Состав каталогов приведен ниже.

- Каталог `v1/` содержит `system_base`, `worker_1`..`worker_8` (восемь
  найденческих ролей: Грамотность, Форматирование, Стиль и тон, Соответствие
  гайду, Терминология, Критик, Согласованность, Лексикон) и `extractor`
  (извлечение гайда из DOCX).
- Каталог `v2/` содержит `system_base`, `language`, `guide_local`, `structure`,
  `terminology`, `consistency`, `verifier`.

Модуль `workers.py` выбирает каталог по переменной `PROMPT_VERSION`. В
системный промпт добавляются общие правила (группа `GENERAL_GROUP`), базовые
формулировки и, если гайд содержит поле `extra_instruction`, ее текст. Кэш
клиента модели включает версию промпта в пространство ключей, поэтому правка
шаблона сама по себе сбрасывает кэш ответов. Формат ответа задан строго
JSON-схемой в шаблоне; менять поля можно только вместе с парсером в `workers.py`
и правилами отбрасывания в `schemas.py`.

В проекте действуют три правила промптинга, перечисленные ниже.

- Описания полей и примеры пишутся по-русски, служебные заметки для модели
  тоже: она читает русскоязычный текст.
- В промпты не вводят идентификаторы правил. Модель оперирует переданным
  фрагментом гайда, идентификатор проставляет код по контексту воркера.
- Правки текстов правил и промптов обязаны проходить `make regression`, а если
  они затрагивали верификатор, еще и оценочный прогон.

## Оценочный прогон как приемка правил

Каталог `backend/eval/` содержит 20 эталонных текстов с ожидаемыми находками
(файл `cases.yaml`). Скрипт `run_eval.py` прогоняет их через живой конвейер
против настроенной модели и считает полноту по правилам, блокам и подсказкам с
порогами (например `min_rule_recall: 0.80`). Запуск выполняется командой
`cd backend && python -m eval.run_eval` и требует настроенных переменных
`LLM_*`; результат отдается в формате JSON или JUnit.

Этот же механизм покрыт тестами на мок-провайдере (`test_eval_runner.py`), а CI
не запускает его против живой модели.

## Порядок добавления правила

Полная процедура добавления правила состоит из шести шагов.

1. Сформулируйте идентификатор и тексты: `rule`, `generalization`, примеры
   хороших и плохих текстов, строгость, группу. Решите, чем правило
   исполняемо: регулярное выражение это Vale-стиль, морфология функция в
   `custom_checks.py`, смысл только модель. Значение `engine: manual` не
   назначают: оставляют vale или python с `automation: partial`.
2. Добавьте запись в список `RULES` реестра со всеми метаданными. Ставьте
   `machine_verifiable: True` только если находку можно проверить сравнением
   строк; иначе верификатор будет срезать живые замечания.
3. Запустите `python backend/styleguide/_generate.py` и проверьте diff файла
   `rules.yaml`.
4. Создайте Vale-файл или Python-функцию и подключите ее в
   `run_all_custom_checks`.
5. Добавьте регрессионный кейс в `regression_checks.py`: плохой текст обязан
   дать срабатывание правила, хороший не дать.
6. Прогоните `make lint && make test && make regression`, а при изменении
   модельного слоя еще и оценочный прогон.
