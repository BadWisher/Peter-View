# Рабочее окружение

Эта страница описывает рабочий цикл разработчика: клонирование репозитория,
запуск стека локально, правка кода, прогон тестов и линтера. Она нужна тем, кто
будет изменять код или документацию сервиса.

Страница отвечает на вопросы: что должно быть установлено, как поднять стек для
разработки, как запускать проверки без пересборки образа и как включить
горячую перезагрузку backend. Эксплуатационное развертывание на сервере
описано в **Implementation Guide** на странице **Развертывание**. Для проверки
текста без изменения кода достаточно раздела **User Guide**.

## Требования к хосту

Для локальной работы нужны перечисленные ниже компоненты.

- Docker Engine с дополнением compose версии 2. Поддерживается и прежняя
  команда `docker-compose`: скрипт `deploy.sh` сам определяет доступную.
- Git.
- Python 3.12 на хосте, если тесты и линтер запускаются вне контейнера. Код
  backend рассчитан на 3.12, как и образ контейнера.
- Около 4 гигабайт свободной памяти под контейнеры: до 2 гигабайт занимает
  backend, до 1.5 гигабайт LanguageTool.

Сборочных инструментов для фронтенда не требуется. Ни Node, ни npm, ни сборщик
не нужны: фронтенд это обычные файлы JS и CSS, а nginx раздает их как статику.

## Первый запуск

Клонирование и запуск выполняются командами из блока ниже.

```bash
git clone https://github.com/BadWisher/Peter-View
cd Peter-View
cp .env.example .env          # deploy.sh сделает это сам, если .env нет
./deploy.sh
```

Скрипт собирает три образа (`backend`, `frontend` и готовый `languagetool`),
поднимает контейнеры и опрашивает адрес `http://localhost:3080/` до 30 раз с
интервалом в 2 секунды, пока фронтенд не ответит. LanguageTool на JVM
просыпается последним, на это уходит от полутора до двух минут. Когда скрипт
напечатает список адресов, интерфейс доступен по адресу
`http://localhost:3080`, а документация API (если она включена) по пути
`/api/docs`.

Первый вход выполняется под учетной записью `admin` с паролем `admin`, после
чего пароль следует сменить. Порядок работы с учетными записями описан в
**User Guide** на странице **Учетные записи и роли**.

## Ручной запуск compose-командами

Когда нужно подменить compose-файл или поднять только один сервис, удобнее
работать напрямую командами compose. Набор типовых команд приведен ниже.

```bash
docker compose up -d languagetool          # движок орфографии
docker compose build backend               # пересборка после правок Python
docker compose up -d backend               # запуск одного сервиса
docker compose logs -f backend
```

Переменные читаются из файла `.env`, лежащего рядом с `docker-compose.yml`;
сервис backend подключает его через `env_file`. Часть значений переопределена
прямо в блоке `environment:` compose-файла, и из `.env` они не переносятся.
Это ограничение переопределения разобрано в **Implementation Guide** на странице
**Переменные окружения**.

## Команды Makefile

В корне репозитория лежит **Makefile** с типовыми командами. Он работает с тем
же `docker compose` и сам добавляет overlay корпоративного прокси, если в `.env`
установлено `PROOFREADER_CORP_PROXY=true`. Состав команд показывает таблица
ниже.

| Команда | Действие |
|---|---|
| `make deploy` | то же, что `./deploy.sh` |
| `make update` | `git pull --ff-only` и пересборка через `deploy.sh` |
| `make logs`, `make ps`, `make down` | управление поднятым стеком |
| `make backup` | ручной снимок `/app/data` в `./backups` внутри контейнера backend |
| `make config` | `docker compose config --quiet`, проверка валидности файлов |
| `make lint` | `ruff check` по каталогам `backend/app`, `backend/eval`, `backend/tests` |
| `make test` | `pytest -q` на хосте, для чего нужен Python 3.12 с dev-зависимостями |
| `make regression` | регрессионные проверки правил внутри контейнера backend |
| `make ci-local` | lint, test, проверка конфигов и сборка образов, как это делает CI |
| `make prod-config` | валидация prod-overlay, требует переменных `IMAGE_SHA` и `GHCR_REPOSITORY` |
| `make config-corp-proxy` | валидация compose с корпоративным прокси |

## Тесты и линтер вне контейнера

Чтобы не пересобирать образ на каждую правку, зависимости ставятся в
виртуальное окружение хоста, а проверки запускаются командами ниже.

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r backend/requirements-dev.txt
make lint
make test
```

Конфигурация pytest находится в корневом `pyproject.toml`: значения
`pythonpath=["backend"]` и `testpaths=["backend/tests"]`. Поэтому запуск
выполняется из корня репозитория, а не из каталога `backend/`. Подробно о
составе тестов и их покрытии написано на странице **Тесты и регрессия**.

Команда `make regression` требует поднятого LanguageTool, потому что проверки
обращаются к нему по HTTP. По этой же причине она выполняется внутри
контейнера, а не на хосте.

## Горячая перезагрузка backend

В образе сервер uvicorn запускается без флага `--reload`. Для разработки с
перезапуском на сохранение процесса поднимают вручную. Команды приведены ниже.

```bash
docker compose up backend   # без -d, остановка по Ctrl-C
docker compose exec backend python -m uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

Чтобы флаг `--reload` видел правки с хоста, каталог `./backend/app` на время
разработки пробрасывается в контейнер томом. В штатном compose-файле исходники
копируются в образ, и томов нет.
